# 클라우드 세이브 — 기기 토큰 + 연동 코드

작성일: 2026-07-27
대상: 새 공용 파일 `cloud.js` · 8개 게임 `index.html` · `help.js` 사용 게임 7종 · Supabase 스키마
배포: **베타 먼저** (`beta/`). 상용 반영은 검증 후 별도 판단.

## 1. 배경

진행 상황이 전부 `localStorage`에만 있다. 브라우저 데이터를 지우거나 기기를 바꾸면
육성 중인 선수·세이브 슬롯·환생 유산이 완전히 사라진다.

은퇴한 커리어는 이미 Supabase `hof` 테이블에 올라가지만 되찾을 수 없다.
신원이 `grow-player-id`(localStorage의 랜덤 문자열)뿐이라, 브라우저를 지우면
**DB에 기록이 멀쩡히 남아 있어도 그게 내 것임을 증명할 수단이 없다** (`match.js:41-48`).

iOS 사파리는 7일간 방문이 없으면 사이트 데이터를 지울 수 있어(ITP) 실제로 발생하는 문제다.

## 2. 목표와 비목표

**목표**
- 진행 중인 세이브를 서버에 자동 백업한다.
- 사용자가 코드 하나로 새 기기에서 8개 게임 기록을 이어받는다.
- **여러 기기를 오가며 플레이해도 최신 진행이 따라온다.**
- 오프라인에서 게임이 지금과 똑같이 동작한다.

**비목표**
- 계정·로그인·이메일. 도입하지 않는다 (계정은 내부 개념일 뿐 사용자에게 노출되지 않는다).
- 실시간 동기화. 접속·전환 시점에만 맞춘다.
- 자동 병합. 충돌은 사용자가 고른다 (5.3 참조).
- 코드를 발급하지 않은 사용자의 복구. 불가능하다 (7절 참조).

## 3. 결정 사항 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 신원 | 기기 토큰 (128비트 무작위, localStorage) | 사용자가 외울 필요 없음 |
| 익명 인증 | **쓰지 않음** | 토큰 탈취 위험이 리프레시 토큰과 동일한데 복잡도만 증가 |
| DB 저장 형태 | 토큰의 **SHA-256 해시**만 저장 | DB 유출 시에도 사용 불가 |
| 테이블 접근 | 클라이언트 직접 접근 차단, `security definer` 함수로만 | 목록 조회·덤프 불가 |
| 연동 코드 | 사용자가 발급, **일회용**, 해시로만 저장 | 사고 복구 가능 + 유출 피해 한정 |
| 코드 재발급 | 새로 발급하면 옛 코드 무효 | 유출 대응 |
| 코드를 넣으면 | 그 기기가 **같은 계정에 연결**된다 (소유권 이전 아님) | 여러 기기를 오갈 수 있어야 함 |
| 여러 기기 | **지원한다.** 계정 하나에 기기 여러 대 | 사용자 요구 |
| 충돌 판정 | 서버 시각 + 기기별 "미전송 변경" 플래그 | 기기 시계를 믿지 않기 위해 |
| 충돌 시 | **사용자가 고른다** (자동 병합 없음) | 두 기록을 섞으면 어느 선수가 진짜인지 정할 수 없음 |
| 진입점 | 각 게임 타이틀 화면 버튼 → 모달 | 설정 화면이 없음. `help.js`의 모달 스타일 재사용 |
| 동기화 표시 | 우측 상단 알약, 자동 소멸 | 진행을 막지 않음 |

## 4. 데이터 모델

### 4.1 테이블

세이브는 **기기가 아니라 계정**에 매단다. 그래야 여러 기기가 같은 기록을 공유한다.

```sql
create extension if not exists pgcrypto with schema extensions;

-- 계정 — 사용자에게 노출되지 않는 내부 개념. 세이브의 실제 주인.
create table public.cloud_account (
  id      uuid primary key default gen_random_uuid(),
  created timestamptz not null default now()
);

-- 기기 — 한 계정에 여러 대가 붙는다. 토큰 원문은 저장하지 않는다.
create table public.cloud_device (
  token_hash text primary key,
  account_id uuid not null references public.cloud_account(id) on delete cascade,
  created    timestamptz not null default now(),
  seen       timestamptz not null default now()
);

-- 게임별 세이브. 계정당 게임당 한 행.
create table public.cloud_save (
  account_id uuid not null references public.cloud_account(id) on delete cascade,
  game       text not null,
  data       jsonb not null,
  updated    timestamptz not null default now(),   -- 서버 시각. 기기 시계를 쓰지 않는다
  primary key (account_id, game)
);

-- 연동 코드. 원문 대신 해시. 일회용.
create table public.cloud_code (
  code_hash  text primary key,
  account_id uuid not null references public.cloud_account(id) on delete cascade,
  created    timestamptz not null default now()
);
```

네 테이블 모두 RLS를 켜고 **정책을 하나도 만들지 않는다.** 정책이 없으면 `anon` 역할은
아무것도 못 한다. 접근은 아래 `security definer` 함수로만 이뤄진다.

### 4.2 함수

모두 `security definer`, `search_path = public, extensions` 고정.

| 함수 | 인자 | 하는 일 |
|---|---|---|
| `cloud_push(p_token, p_game, p_data)` | 토큰·게임·세이브 | 세이브를 upsert하고 **새 `updated`(서버 시각)를 반환** |
| `cloud_meta(p_token)` | 토큰 | 게임별 `updated`만 반환 (본문 없이 — 충돌 판정용, 가볍다) |
| `cloud_pull(p_token, p_game)` | 토큰·게임(널이면 전체) | 세이브 본문과 `updated` 반환 |
| `cloud_issue(p_token)` | 토큰 | 그 계정의 기존 코드 삭제 후 새 코드 발급, **원문을 1회 반환** |
| `cloud_claim(p_token, p_code)` | 새 기기 토큰·코드 원문 | 코드 검증 후 **그 기기를 코드의 계정에 연결**, 코드 삭제 |

해시는 `encode(digest(p_token, 'sha256'), 'hex')`.

`cloud_push`가 새 `updated`를 돌려주는 것이 중요하다. 클라이언트는 이 값을
`lastSyncedUpdated`로 저장해두고, 다음 접속 때 서버 값과 비교해 다른 기기의 변경을 감지한다.

**처음 보는 토큰**이 오면 `cloud_push`·`cloud_meta`가 계정을 새로 만들고 기기를 붙인다.
즉 별도 가입 절차가 없다.

### 4.2.1 코드 형식 — 설계 중 바뀐 부분

브레인스토밍 초반에는 `한강-불꽃-7382` 같은 외우기 쉬운 단어 코드를 그렸다.
**최종 설계에서는 이를 버리고 무작위 코드를 쓴다.**

```
GRW7-K2M9-XQ4T-B8HN-3PZR-6VWD
```

이유는 두 가지다. 첫째, 최종 UX가 **클립보드 복사**라 사용자가 외우거나 옮겨 적을
필요가 없어졌다. 둘째, 시도 횟수 제한을 서버에서 걸 수 없기 때문이다 — 코드 해시가
일치하지 않으면 어느 행의 카운터를 올려야 할지 알 수 없다. **무차별 대입 방어를
전적으로 코드 엔트로피에 의존해야 하므로** 단어 코드의 49비트로는 부족하다.

24자 base32(약 120비트)에 4자씩 하이픈을 넣어 읽기 쉽게 만든다. 사용자가 직접
입력해야 하는 상황(복사 실패)에 대비해 혼동되는 문자(`0/O`, `1/I/L`)는 제외한다.

### 4.3 연결 동작 (`cloud_claim`)

1. `p_code` 해시로 `cloud_code` 조회. 없으면 실패 반환.
2. 새 기기(`p_token` 해시)의 `account_id`를 **코드가 가리키는 계정으로 설정**한다
   (`cloud_device` upsert).
3. 코드 행을 삭제한다 (일회용).
4. 새 기기가 원래 갖고 있던 계정에 다른 기기가 하나도 없으면 그 계정은 고아가 된다.
   세이브가 남아 있을 수 있으므로 **삭제하지 않고 그대로 둔다.** 접근 경로가 사라질 뿐이다.

세이브를 옮기지 않는다는 점이 핵심이다. 두 기기가 같은 계정을 **공유**하게 될 뿐이며,
이후 어느 쪽에서 플레이하든 5절의 동기화 규칙에 따라 최신 상태가 양쪽에 반영된다.

> 4번의 고아 계정은 저장 공간을 조금 낭비한다. 사용량이 문제가 되면 나중에
> "기기가 하나도 없고 90일 이상 갱신 없는 계정"을 정리하는 배치를 붙인다.
> 이번 범위에서는 하지 않는다.

## 5. 동기화 정책

`localStorage`가 항상 주(主)다. 클라우드는 그 사본이다. 오프라인에서 게임은 지금과 똑같이 동작한다.

### 5.1 기기가 들고 있는 두 값

게임별로 localStorage에 둔다.

| 값 | 뜻 |
|---|---|
| `lastSyncedUpdated` | 마지막으로 서버와 맞춘 시점의 서버 `updated` 값 |
| `dirty` | 마지막 전송 이후 로컬 세이브가 바뀌었는지 (참/거짓) |

`dirty`는 **그 기기 안에서만 쓰는 값**이라 시계가 필요 없다. 기기 시계는 어디에도 쓰지 않는다.

### 5.2 올리는 시점

`cloud.js`는 게임의 `save()`를 가로채지 않는다. 아래 시점에만 밀어넣는다.

- 시즌 종료 · 은퇴 · 환생 — 게임이 `Cloud.mark()`를 호출
- 마지막 전송 후 2분 이상 지난 상태에서의 저장
- `visibilitychange`로 페이지가 숨겨질 때 (`fetch` + `keepalive`)

성공하면 서버가 돌려준 `updated`를 `lastSyncedUpdated`에 넣고 `dirty`를 내린다.

### 5.3 받아오는 시점과 충돌 판정

**타이틀 화면 진입 시** `cloud_meta`로 게임별 `updated`만 가볍게 받아 비교한다.

| `dirty` | 서버가 더 최신 (`updated > lastSyncedUpdated`) | 동작 |
|---|---|---|
| 아니오 | 예 | **자동으로 받아온다.** `☁️ 다른 기기 기록을 불러왔어요` 토스트만 띄운다 |
| 아니오 | 아니오 | 아무것도 안 한다 |
| 예 | 아니오 | 올린다 |
| 예 | 예 | **충돌 — 사용자에게 묻는다** |

A에서 놀다 B로 갔다가 다시 A로 오는 흐름은 첫 줄에 해당해 아무것도 묻지 않고 조용히 맞춰진다.
충돌은 두 기기에서 각각 진행했을 때만 뜬다.

판정은 **게임별로 따로** 한다. 루키에서 충돌이 나도 아이돌은 조용히 넘어간다.

### 5.4 충돌 화면

```
  ⚠️ 두 기기에서 각각 진행됐어요

  이 기기        ⚾ 더 루키 — 고교 2학년
  다른 기기      ⚾ 더 루키 — 프로 3년차   (2시간 전)

  [ 이 기기 것 쓰기 ]  [ 다른 기기 것 쓰기 ]
```

- `이 기기 것 쓰기` → 로컬을 그대로 올린다. 서버 기록을 덮는다.
- `다른 기기 것 쓰기` → 서버 것을 받아 로컬을 덮는다.
- **자동 병합은 하지 않는다.** 두 육성 기록을 섞으면 어느 선수가 진짜인지 정할 수 없다.
- 고르기 전에는 어느 쪽도 바꾸지 않는다. 취소하면 이번 실행에서는 다시 묻지 않는다
  (게임을 막지 않기 위해). 다음 실행 때 다시 뜬다.

"2시간 전"은 서버 `updated`와 현재 시각의 차이다. 기기 시계가 틀어져 있으면 이 표시만
어긋나고 판정에는 영향이 없다.

### 5.5 실패 처리

모든 실패를 삼킨다. `match.js`와 같은 방식이다. 게임 진행은 절대 막지 않는다.
전송 실패 시 `dirty`를 유지해 다음 기회에 다시 시도한다.

### 5.6 베타 격리

`localStorage`가 이미 `beta::`로 격리되므로 베타 기기 토큰이 상용과 자동으로 분리된다.
계정도 따로 만들어진다. 상용 세이브를 오염시키지 않는다.

다만 `cloud_save.game`은 같은 값(`rookie` 등)을 쓰므로 **같은 테이블에 베타 행이 섞인다.**
구분이 필요하면 `game`에 `beta:` 접두어를 붙인다. 이번 구현에서 그렇게 한다.

## 6. 클라이언트 구조

새 파일 `cloud.js` 하나가 8종 공용이다. 게임 로직은 건드리지 않는다.

```
window.Cloud = {
  init(game),      // 타이틀 화면 로드 시 1회. 동기화 판정까지 여기서 한다
  mark(),          // "지금은 중요한 순간" 신호 → 즉시 전송
  touch(),         // 로컬이 바뀌었다는 신호 → dirty 세움
  openModal(),     // 🔗 기록 연동 모달
}
```

세이브를 읽고 쓰는 방법은 게임이 넘겨주지 않고 **`cloud.js`가 게임별 키 목록으로 안다.**
게임 코드 변경을 `Cloud.mark()`/`touch()` 호출 두 곳으로 줄일 수 있다.

- 읽기 — 그 게임의 키 전부를 모아 하나의 객체로
- 쓰기 — 객체를 localStorage에 되돌려 쓰고 `location.reload()`

### 6.0 실제 저장 키 (코드에서 확인함)

| 게임 | `SAVE_KEY` | 배틀 키 |
|---|---|---|
| rookie | `rookie-save-v1` | `grow-battle-v1` |
| idol | `trainee-save-v1` | `grow-battle-idol-v1` |
| stock | `investor-save-v1` | `grow-battle-stock-v1` |
| dev | `devgrow-save-v1` | `grow-battle-dev-v1` |
| chef | `chef-save-v1` | `grow-battle-chef-v1` |
| stream | `streamer-save-v1` | `grow-battle-stream-v1` |
| soccer | `winger-save-v1` | `grow-battle-soccer-v1` |
| unicorn | `unicorn-save-v1` | 없음 (`unicorn-founded` 사용) |

7종은 `SAVE_KEY + "-slots"`, `SAVE_KEY + "-legacy"`를 함께 쓴다. 유니콘은 둘 다 없고
`unicorn-founded`가 있다.

**`grow-hof-v1`(명예의 전당)만 8종이 공유한다.** 배틀 키는 게임별로 다르므로 공유가 아니다
(루키만 접미사 없이 `grow-battle-v1`이라 공유처럼 보이지만 루키 전용이다).

따라서 게임별 세이브에 넣으면 서로 덮어쓰는 키는 `grow-hof-v1` 하나뿐이며,
이것만 `game = "_shared"` 행으로 따로 저장한다.

`grow-auto-mini`(미니게임 자동 진행)와 `grow-player-id`는 **기기 설정**이라 동기화하지 않는다.

각 `index.html` 변경은 두 줄이다.

```html
<button class="btn btn-ghost" id="btn-cloud">🔗 기록 연동</button>
<script src="../cloud.js"></script>
```

### 6.1 모달

`help.js`가 쓰는 `.av-overlay` / `.av-modal` 스타일을 재사용한다.

```
  🔗 기록 연동

  이 기기의 기록은 자동으로 백업되고 있어요.
  다른 기기에서도 이어서 하려면 연동 코드를 받아
  그 기기에 붙여넣으세요. 한 번 연결해두면
  8개 게임 기록이 양쪽에서 자동으로 맞춰져요.

  [ 📋 계정 연동 코드 복사하기 ]

  ─────────────────────────────
  다른 기기에서 쓰던 코드가 있나요?
  ┌──────────────────────┐
  │                      │  [ 불러오기 ]
  └──────────────────────┘
```

- 복사 버튼: 누르면 `cloud_issue` 호출 → 코드를 **클립보드에 복사하고 화면에도 표시**한다.
  클립보드는 다른 걸 복사하면 날아가므로 화면 표시가 필수다.
  버튼은 1.5초간 `복사됨 ✓`으로 바뀐다.
- 이미 발급한 적이 있으면 버튼 문구를 `🔄 새 코드 발급 (지금 코드는 무효가 돼요)`로 바꾼다.
  발급 이력은 localStorage 플래그로 판단한다.
- `navigator.clipboard`가 없거나 거부되면(비 HTTPS·구형 브라우저) 코드를 화면에 크게
  띄우고 "길게 눌러 복사하세요"로 안내한다.

### 6.2 연결 확인

코드를 넣으면 `cloud_claim`으로 기기를 계정에 붙인 뒤, `cloud_pull`로 **미리 받아**
무엇이 들어올지 보여준다. 확인 전에는 로컬을 바꾸지 않는다.

이 화면은 5.4의 충돌 화면과 같은 자리에서 다른 문구로 뜬다. 처음 연결하는 순간에는
로컬에도 진행이 있을 수 있으므로 사실상 같은 판단을 해야 하기 때문이다.

판정은 **게임별로** 한다. 한쪽에만 기록이 있는 게임은 물어볼 게 없으므로 자동으로 합친다.
양쪽 모두 기록이 있는 게임만 고르게 한다.

```
  🔗 기기를 연결했어요

  자동으로 합쳐진 기록
    🎤 아이돌     — 연습생 2개월   (다른 기기)
    🍳 요리사     — 3성 셰프       (이 기기)

  ⚠️ 양쪽 모두 기록이 있어요. 골라주세요.
    ⚾ 더 루키
       ○ 이 기기    고교 2학년
       ● 다른 기기  프로 3년차     (2시간 전)

  [ 연결 완료 ]  [ 취소 ]
```

- 한쪽에만 있는 게임 → 있는 쪽을 그대로 쓴다. **게임 단위 병합은 안전하다.**
  루키는 이 기기 것, 아이돌은 저 기기 것이 될 수 있다.
- 양쪽에 있는 게임 → 라디오로 고른다. 기본 선택은 **서버가 더 최신이면 다른 기기**,
  아니면 이 기기다.
- `취소`하면 연결은 이미 됐지만(코드는 소모됐다) 로컬은 그대로 둔다. 다음 실행 때
  5.3의 판정이 다시 돌아 충돌 화면이 뜬다.

요약 문구는 게임별 세이브에서 뽑는다. 게임마다 형태가 달라 `cloud.js`가 알기 어려우므로,
**요약 함수를 `cloud.js` 안에 게임별로 모아둔다.** 세이브 구조만 알면 되는 순수 함수라
게임 코드를 건드리지 않아도 된다. 요약을 못 만드는 게임은 `기록 있음`으로만 표시한다.

> 이 화면은 타이틀 화면에서만 뜬다. 다른 게임의 요약을 보여주려면 그 게임의
> `summarize`가 필요한데, 각 게임 페이지는 자기 것만 로드한다. 그래서 **요약 함수를
> `cloud.js` 안에 게임별로 모아둔다.** 세이브 구조만 알면 되는 순수 함수라 가능하다.

### 6.3 동기화 표시

우측 상단 고정. 반투명 알약. 게임 화면을 가리지 않는다.

| 상태 | 표시 | 지속 |
|---|---|---|
| 전송 중 | `☁️ 동기화중…` | 완료까지 |
| 성공 | `✓ 저장됨` | 1.5초 후 사라짐 |
| 실패 | `오프라인` | 2초 후 사라짐 |

`prefers-reduced-motion`을 존중해 애니메이션을 끈다.

## 7. 한계 (문서에 남겨야 하는 것)

- **코드를 발급하지 않은 사용자는 복구할 수 없다.** 서버에 세이브가 있어도 소유 증명 수단이 없다.
  이를 줄이기 위해 **첫 은퇴 직후 1회** 발급을 권하는 안내를 띄운다. 그 외에는 조르지 않는다.
- **코드를 잃으면 끝이다.** 이메일이 없으므로 재발급도 연결된 기기에서만 가능하다.
- **동시에 두 기기에서 플레이하면 충돌 화면을 보게 된다.** 자동 병합은 하지 않으므로
  한쪽 진행은 버려진다. 번갈아 쓰는 것은 매끄럽지만 동시 진행은 그렇지 않다.
- **오프라인으로 오래 논 뒤 다른 기기 진행과 만나면 충돌이 난다.** 이 경우 어느 쪽이
  "더 많이 진행했는지"를 시스템이 알 수 없어 사용자가 골라야 한다.
- 토큰을 탈취당하면 세이브에 접근할 수 있다. 새 코드를 발급해도 옛 토큰은 무효화되지 않는다.
  (토큰 회전은 이번 범위 밖. 필요해지면 `cloud_device`에 `revoked` 플래그를 추가한다.)
- 연결을 끊는 기능이 없다. 기기를 남에게 넘길 때 그 기기는 계속 계정에 붙어 있다.
  (필요해지면 "이 기기 연결 끊기"를 추가한다. 토큰을 새로 만들면 되므로 간단하다.)

## 9. 검증

`docs/` 아래 기존 방식대로, 테스트 러너 없이 확인한다.

| 대상 | 방법 |
|---|---|
| DB 함수 | Supabase에 직접 RPC 호출 — 발급·연결·코드 재사용 거부·잘못된 코드·처음 보는 토큰 |
| RLS 잠금 | anon 키로 네 테이블에 직접 SELECT/INSERT 시도 → 전부 거부되는지 |
| 기기 연결 | A 저장 → 코드 발급 → B 연결 → B에서 A 기록이 보이는지 |
| 왕복 동기화 | A 플레이 → B 플레이 → **A 재접속 시 자동으로 B 진행이 반영되는지** (핵심 시나리오) |
| 충돌 판정 | 4가지 조합(`dirty` × 서버 최신)이 각각 의도한 분기로 가는지 |
| 충돌 화면 | 고르기 전에는 양쪽 모두 안 바뀌는지, 고른 뒤 정확히 한쪽만 남는지 |
| 모달·버튼·클립보드 | jsdom (`scratchpad/dom-test.js` 패턴). 클립보드는 스텁 |
| 오프라인 | `fetch`를 실패시켜 게임이 정상 진행되고 `dirty`가 유지되는지 |
| 베타 격리 | 베타 토큰·계정이 상용과 다른지, `game`에 `beta:` 접두어가 붙는지 |

CSS 렌더링은 여전히 검증할 수 없다. 배포 후 실기기 확인이 필요하다.
