### 🔴 F2. **결승골이 잘못된 카드에 붙습니다** — `engine.js:563-574`

`markDecisive()`가 자기 주석과 다르게 돕니다. 주석은 *"이긴 팀이 마지막으로 앞서기 시작한 골"*인데,
`lead === 1`을 **실점 카드에서도** 만족시켜서 그 카드에 결승골이 붙어요.

```js
for (const cd of cards) {
  if (cd.result === "concede") b += 1; else a += 1;
  const lead = win === 0 ? a - b : b - a;
  if (lead === 1) { for (const x of cards) x.decisive = false; cd.decisive = true; }  // ← 실점 카드도 들어옵니다
}
```

**독립 오라클과 대조한 실측** (`engine-test.js` — 축구의 정의 *"이긴 팀의 (진 팀 최종 점수 + 1)번째 골"*을
검사가 직접 계산합니다. 엔진 출력을 정답으로 삼지 않았어요):

| | |
|---|---|
| 판정 난 경기 | 930 |
| **어긋남** | **186 (20.0%)** |
| 그중 "이긴 경기인데 실점 카드에 결승골" | 78 |

**화면에 보이는 결과** (3,000경기 실측):

| 무슨 일이 | 판정 경기 2,318건 중 |
|---|---|
| 😱 **진 경기인데 `🏆 결승골!!` 배너 + 색종이가 터짐** | **90건 (3.9%)** |
| 😶 이긴 경기인데 결승골이 실점 카드에 붙어 **축포가 조용히 안 뜸** | 125건 (5.4%) |

예: `1:2` — `concede concede goal◀결승골`. **진 경기에서 내 골이 결승골이 됩니다.**

**고치는 방향** (한 함수로 끝납니다)

```js
function markDecisive() {
  if (us === them) return;
  const weWon = us > them;
  const need = (weWon ? them : us) + 1;      // 진 팀 최종 점수 + 1
  let n0 = 0;
  for (const cd of cards) {
    const ours = cd.result === "goal" || cd.result === "assist";
    const theirs = cd.result === "concede";
    if (weWon ? ours : theirs) { n0 += 1; if (n0 === need) { cd.decisive = true; return; } }
  }
}
```

> ✅ **`decisive`를 두 번 되채우지는 않습니다.** engineer의 `markDecisive()`와 director의 설명은
> **같은 것을 말하고 있어요** — 엔진이 `end` 카드를 내기 직전에 이미 그린 카드 객체를 되채우고,
> 화면은 그 **같은 객체**를 기억해 뒀다가 휘슬 때 다시 봅니다. 되채움은 한 번뿐이에요.
> (`match-scene.js`에는 자체 `markDecisive`가 없습니다. 확인했습니다.)
> 문제는 되채우는 **횟수**가 아니라 **어느 카드**냐입니다.

### 🟠 F3. 순간 카드 빈도가 **계단**입니다 — `engine.js:177-183` · `204`

설계 §2-10은 `ACE_W` 계단을 폐기한 이유를 *"계단이 축을 70→90에서 **2.8배** 튀게 한 주범"*이라고

**동료 전력을 바꿔 보면 계단이 옆으로 통째로 움직입니다** — 내 능력치가 아니라 동료 전력이 정합니다.

>
> **누가 정하나**: designer(§2-4 `isAce`를 계단으로 둘 것인가) · balancer(계수).

### 🟠 F4. (라′) 중립 위반 — 🧱 수비 **카드**가 자동보다 안전합니다 — `engine.js:321-333`

설계 검사 10번은 AUTO/CARD 두 갈래의 기댓값 차이를 **±3%**로 못박았습니다.

```js
if (kind === "defend") {
  const miss = clamp(autoP, 0, 1 - perfect);   // ← perfect가 커지면 miss가 잘립니다
  return r < 1 - miss ? "ok" : "miss";
}
```

`perfect + pConcede > 1`이 되면 `miss`가 `1 − perfect`로 잘려요. 능력치가 높을수록 심해집니다.

| 능력치 | 자동 실점 확률 | 내 카드 실점 확률(실측) | 차이 |
|---|---|---|---|
| 70 | 0.5555 | 0.5590 | +0.6% ✅ |
| 110 | 0.3967 | 0.3797 | **−4.3%** ❗ |
| 150 | 0.2630 | 0.2372 | **−9.8%** ❗ |

식이 맞는지는 **자동 갈래를 따로 실측해서 먼저 확인**했습니다 (능력치 90: 실측 0.4845 vs 식 0.4798).

능력치 150 수비수는 *"내가 맡으면 실점이 10% 덜 난다"*는 보너스를 조용히 받고 있어요.
`sc(x)`가 만들어 준 중립을 `outcome()`의 clamp가 다시 깨뜨립니다.

> **누가 정하나**: balancer. `perfect`를 `1 − pConcede`로 눌러 담을지, 아니면 이 차이를
> 인정하고 `CON`으로 되맞출지가 갈립니다. engineer §4-⑤(전개 카드 도움 4~5배 어긋남)와
> **같은 뿌리**예요 — `succ` 표와 자동 확률이 서로 독립이라 두 갈래가 반드시 어긋납니다.

## 2. ✅ 변이 검증 — 요청하신 3건 + 1건

설계 §12-5가 못박은 *"SPOT을 1로 되돌리면 1번이, sc(x)를 1로 고정하면 12번이,
fatigue가 도움을 세게 하면 11번이 반드시 빨간불"* — **셋 다 잡힙니다.**
`tests/winger2/mutation-test.js`가 소스를 실제로 갈아치워 확인해요
(정규식이 안 걸리면 예외를 던집니다 — "변이했는데 초록불"이 되는 걸 막아요).

| 변이 | 무엇이 빨간불이 되나 | 지금 | 변이 후 |
|---|---|---|---|
| **`SPOT` 4.00 → 1** | A. 능력치 130 시즌 생산량 (문턱 fw 골 ≥ 18 · wg 도움 ≥ 26) | 골 **22.3** · 도움 **34.4** | 골 **13.0** · 도움 **18.7** ❌ |
| **`sc(x)` → 1** | B. 동료 능력치가 자동 확률에 실린다 (실점 ≥12%↓ · 팀 득점 ≥7%↑) | 실점 **25.3%↓** · 득점 **19.2%↑** | 실점 **−0.8%** · 득점 **−4.8%** ❌ |
| **`fatigue`가 도움을 셈** | C. 도움 뒤/골 뒤 카드 획득비 (≥1.18) · mf150 카드/경기 (≥1.55) | **1.331** · **1.622** | **1.094** · **1.480** ❌ |
| **`condMul`을 STEP 3에도** | D. 컨디션 0→100 수비 장면 점유율 변화 (≤+2%) | **−0.42%** | **+9.50%** ❌ |

> ### 🚨 문턱은 전부 검사 파일에 **직접 적었습니다**
> `_t.K`나 `MOM_MIN`에서 읽어 오면 상수를 바꿔도 검사가 따라가서 아무것도 안 잡혀요.
> `_t.K`는 **"엔진이 실제로 쓰는 값"과 "설계 §3-1 표"를 대조하는 데만** 씁니다.

> ### 🕳️ 검사를 짜다 제가 먼저 빠진 함정 — 픽스처가 변이를 무력화합니다
> 처음엔 **동료를 전부 `str: 70`으로** 두고 `sc(x) → 1` 변이를 걸었는데,
> **숫자가 소수점까지 똑같이 나왔습니다.** `sc(70) = 1`이라 동료 쪽에서는 변이가 항등이고,
> 내 쪽은 `outcome()`의 clamp가 차이를 먹어 버렸거든요.
> **초록불인데 아무것도 안 지키는 검사가 그 자리에서 만들어졌습니다.**
> 그래서 B는 동료 전력을 **45 vs 95로 갈라서** 잽니다. 이 이유를 검사 주석에 남겼어요.
