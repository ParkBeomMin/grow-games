## 2. 경기 엔진 — 확정 산식

**점진 확정**입니다. 카드마다 그 자리에서 굴리고, **마지막 카드 전까지 스코어가 미확정**이에요.
`splitMine` · `deriveOppGoals` · `holdConceded` · 에이스 계단은 **전부 폐기**합니다.

### 2-1. 한 경기의 뼈대

```
카드 N장 (N_MIN 6 ~ N_MAX 8)
  |스코어차| ≥ 3 이 되면 6장에서 끊습니다 (이미 끝난 경기)

카드 k = 1..N 을 순서대로 해결합니다.
```

### 2-2. STEP 1 — 이 장면의 주인은 누구인가

```js
atkW = teamAtk / (teamAtk + oppDef);
defW = oppAtk  / (oppAtk  + teamDef);

p(우리 공격) = SCENE_ATK * atkW / (atkW + defW);
p(상대 공격) = SCENE_ATK * defW / (atkW + defW);
p(중립)      = 1 - SCENE_ATK;              // 중원 공방 필러 카드 — 아무도 주인공이 아님
```

> ⚠️ **스코어를 보지 않습니다.** 리드/열세로 장면 배분이 움직이지 않아요.
> 이유와 2차 후보는 §5-3에.

### 2-3. STEP 2 — 결정적 장면(빅찬스)인가

**우리 공격 장면일 때만** 굴립니다.

```js
pBig(k) = BIG_BASE * edge * urgency(k) * condMul;

  edge       = (teamAtk / (teamAtk + oppDef)) / 0.5;        // 1.0이 중립
  urgency(k) = 1 + URG * behind(k) * (k / N);               // behind = 지고 있는 골 수
  clutch(k)  = (k === N && |스코어차| <= 1) ? CLUTCH : 1;    // 마지막 카드 = 추가시간
  condMul    = 0.76 + 0.30 * (condition / 100);             // §2-7
```

> ### ⏱️ `clutch` — 9번째 카드 대신 마지막 카드의 무게를 올립니다 (2026-08-28 판정 · engineer §4-④)
> §5-5가 *"1점 차일 때 카드가 하나 더"*라고 적었는데 `N_MAX 8`과 충돌합니다.
> **9번째 카드는 넣지 않습니다** — 생산량이 늘어 곡선이 통째로 움직여요.
>
> 대신 **마지막 카드가 1점 차 이내면 그 카드가 추가시간(`90+1~5분`)이 되고,
> 결정적 장면이 될 확률이 올라갑니다.** **`CLUTCH = 1.25`** (확정 — 실측 ①-F).
>
> **1.35에서 내렸습니다.** 시즌 골이 **+3.6%**로 ±3% 밴드를 아슬하게 넘었어요.
> 밴드를 넓히지 않은 이유는 셋입니다 —
> ① ±3%는 제가 임의로 정한 게 아니라 **(라′) 중립 기준을 이어받은 것**이고,
>    그 밴드가 곧 원칙 ④(*새 축을 얹는 것만으로 세지면 안 된다*)의 운영 정의입니다
> ② **`clutch`의 값어치는 세기가 아니라 존재입니다.** 화면에서 느끼는 건 배수가 아니라
>    **`90+3분` 표시와 타이핑 연출**이에요. 1.25도 `urgency`의 최대치(1.36)와 비슷한 크기라
>    효과가 죽지 않습니다
> ③ **한 번 넓히면 다음 항목도 넓히게 됩니다.** 이 저장소가 데인 자리(골든부츠 43%→60%)가
>    정확히 *"조금인데 뭐 어때"*였어요
>
> `urgency`는 **뒤질 때만** 걸립니다(`behind`). `clutch`는 **1점 차로 앞설 때도** 걸려요 —
> §C-3 "긴장이 곧 조작량"의 마지막 조각입니다. 마지막 카드가 상대 공격 장면이면
> 🧱 수비 카드가 그대로 열리니 **수비수도 이 순간을 받습니다.**
>
> 카드 수가 안 늘어 영향이 `CLUTCH` 하나로 통제됩니다.

**빅찬스면 → ⚽ 결정 카드 후보. 아니면 → 🅰️ 전개 카드 후보.**

> ⚠️ **`fatigue`는 여기 없습니다.** STEP 3으로 옮겼어요 —
> `pBig`는 장면의 속성이고 `mineHit`은 사람의 속성이라, 경쟁자 11명을 함께 굴릴 때
> 이 자리에서는 **정의가 안 됩니다** (주인공을 아직 모르니까요).

### 2-4. STEP 3 — 누가 주인공인가

선발 11명 각자에 대해 무게를 구하고 그 비율로 뽑습니다. **내 선수도 그중 하나예요.**

```js
w(i) = posW(카드종류, pos_i)          // 포지션 가중  ← 이게 없으면 센터백이 스트라이커만큼 골을 넣습니다
     * slot_i.X                       // 자리 가중 (결정→g · 전개→a · 수비→d)
     * blend(i)                       // 능력치 혼합 (아래)
     * traitMul(i) * footMul(i) * trustMul(i)
     * fatigue(i)                     // = 1 / (1 + FAT * goalsScored_i)   ← "내가 넣은 골"만
     * (isAce(i, 카드종류) ? spotOf(i) : 1)   // 나 → SPOT · 경쟁자 클럽 에이스 → NPC_SPOT
     * (i === me ? ME_P : 1);

pMe = w(me) / Σ w(i);

blend(i) = st(S1)*0.60 + st(S2)*0.25 + st(S3)*0.15;
```

> ⚠️ **`condMul`은 여기 없습니다.** STEP 2와 판정 창 두 곳뿐이에요 (§2-7).
> 컨디션이 낮다고 감독이 덜 쓰는 건 선발/벤치 결정에서 이미 처리됩니다 — 이중 계상이에요.

**🌟 에이스는 카드 종류마다 따로 뽑습니다.** 한 클럽에 골 에이스 · 도움 에이스 ·
수비 에이스가 각각 한 명이고, 같은 사람일 수도 있어요.

```js
const ACE_POOL = { goal: ["fw"], assist: ["mf", "wg"], defend: ["df"] };
// 그 풀 안에서 해당 카드 종류의 무게가 가장 큰 한 명 → SPOT(나) 또는 NPC_SPOT(경쟁자)
```

### 🔴 내 몫에는 **바닥**이 있습니다 — `FLOOR_SHARE` (2026-08-28 판정 · inspector F3)

```js
w(me) = max(w(me), FLOOR_SHARE * Σ w(i));      // FLOOR_SHARE = 0.12 (제안)
```

**나에게만 겁니다.** 경쟁자에게 걸면 리그 득점이 다시 11명에게 흩어져 골든부츠가 무너져요.

> ### 왜 계단은 두고 바닥을 까나
> inspector가 잰 세 증상은 **하나의 원인**에서 나옵니다 — `SPOT`이 승자독식이라
> ① 능력치 5점에 **2.6배 계단** ② **강팀으로 이적하면 카드가 1/3** ③ 검사 13번이
> 능력치 70 전 포지션 미달(0.31~0.43).
>
> **그런데 한 노브에 목표가 둘 묶여 있습니다.**
> ⓐ **리그 득점 분포** — 골이 소수에게 몰려야 골든부츠가 성립합니다
>    (`career.js:931-934`가 적어 둔 `ACE_W`의 원래 목적: *"이게 없으면 44골이 11명에게
>    고르게 흩어져서 팀 최다 득점자가 8골이 돼요"*)
> ⓑ **내 조작량** — §C-3 "긴장이 곧 조작량" · 검사 13번
>
> **둘을 분리합니다.** ⓐ는 `SPOT`/`NPC_SPOT` 계단이 계속 맡고, ⓑ는 바닥이 맡아요.
>
> **바닥은 아래쪽에서만 작동합니다.** 능력치 110의 `pMe ≈ 0.25`는 안 건드리고,
> 능력치 70의 `≈ 0.06`만 0.12로 올려요 —
>
> | | 바닥 없음 | 바닥 0.12 |
> |---|---|---|
> | 능력치 70 (동료 str 70) | 0.34회 ❌ | **≈ 0.70회** ✅ |
> | 능력치 70 (동료 str 80 · 강팀) | 0.30회 ❌ | **≈ 0.70회** ✅ |
> | 능력치 80 | 0.93회 | 0.93회 (그대로) |
> | 능력치 110 | 1.05회 | 1.05회 (그대로) |
>
> **계단이 2.6배 → 1.3배로 눌리고, 이적 페널티가 사라지고, 검사 13번이 통과합니다.**
> 세 증상이 한 노브로 완화돼요.
>
> ### 그리고 계단을 **화면에 보이게** 합니다 (원칙 ③)
> *"우리 팀 에이스가 되는 순간"*은 버그가 아니라 **좋은 사건**입니다.
> 화면에 안 보이면 노이즈로 읽히고, 보이면 서사가 돼요 —
> 명단·준비 화면에 **🌟 배지**(골/도움/수비 종류별)를 달고, 처음 되는 시즌에
> `🌟 이제 우리 팀의 해결사예요` 한 줄을 띄웁니다. director 항목입니다.
>
> ⚠️ **원칙 ④**: 바닥은 생산량을 늘립니다. 저연차 구간에서만 실질적으로 작동하니
> **목표 곡선 70(5%)에 오히려 가까워질 수 있어요** (현재 1.8%). balancer 확인 항목 ①-I.

### 2-5. STEP 4 — 갈림

```js
if (장면 === "우리 공격") {
  const 주인공 = STEP3(빅찬스 ? "결정" : "전개");
  if (주인공 === me)  → 🔥 순간 카드를 엽니다 (미니게임)
  else                → 자동 굴림:
       pFinish = clamp(FIN * atkW * sc(주인공), 0, 1);
       // 성공하면 그 동료의 골. 여기에 내 도움이 붙는 경로는 아래.
}
if (장면 === "상대 공격") {
  const 주인공 = STEP3("수비");                 // 우리 팀에서 그 장면을 맡는 사람
  if (주인공 === me)  → 🧱 수비 카드를 엽니다
  else                → 자동 굴림:
       pConcede = clamp(1 - (1 - CON * defW) * sc(주인공), 0, 1);
}
if (장면 === "중립") → 필러 텍스트 1줄
```

**`sc(x)` — 자동 확률도 그 장면 주인공의 능력치를 탑니다. 이건 필수입니다.**

```js
const sc = (x) => succ(abilityOf(x), 0.5) / succ(70, 0.5);   // 능력치 70에서 정확히 1
```

> ### 🔒 왜 필수인가
> 자동 확률을 상수로 두면 **능력치가 두 번 실립니다** — 카드는 능력치를 타는데
> 자동은 안 타니, 그 차이가 통째로 새 생산량이 됩니다 (능력치 150에서 도움 **+44%** ·
> 차단 **+84%** · 실점 **−35%**).
>
> 반대로 **카드 쪽에서 능력치를 빼서** 맞추면 중립은 지켜지지만
> **차단에 능력치가 안 실려 수비수만 성장 축이 죽습니다** — 능력치 110에서
> 포지션 격차 **35.8%p**. `POS_AXIS`의 `n`은 레벨만 옮길 뿐 기울기를 못 고쳐요.
>
> **이건 새 발명이 아니라 되살리는 것입니다.** 현행 `deriveOppGoals`(`game.js:1832`)는
> 이미 `((defStat || 40) − 60) / CONC_DEF`로 수비 능력치를 봅니다.
> 제 초안이 `pConcede = CON × defW`로 적으면서 그 항을 떨어뜨린 것이었어요.

**🅰️ 도움이 기록되는 두 경로 — 장면의 성격이 다릅니다**

| 장면 | 도움은 누구에게 | 확률 |
|---|---|---|
| 🅰️ **전개 장면** = "찬스를 **만드는**" 장면 | **그 장면의 주인공에게** (카드든 자동이든) | **항상** — `ASSIST_P2`를 곱하지 않습니다 |
| ⚽ **결정 장면**에서 골이 났을 때 | `ASSIST_P2`(0.75) 확률로 도움자를 **`a` 무게로 지명** (득점자 제외) | `ASSIST_P2` |

> ### 🔴 전개 장면의 도움에 `ASSIST_P2`를 곱하지 마세요 (2026-08-28 판정 · engineer §4-⑤)
> 곱하면 **카드 갈래와 자동 갈래가 4~6배 어긋납니다.**
>
> ```
> 곱하면 →  카드(내가 주인공)   P(내 도움) = perfect              ≈ 0.46
>           자동(내가 주인공)   P(내 도움) = pFinish × ASSIST_P2 × 몫 ≈ 0.07
> ```
>
> **어긋나는 이유는 두 갈래가 다른 사건을 재고 있었기 때문입니다.**
> `ASSIST_P2 × 몫`은 *"동료가 넣은 골에 내가 어시스트로 붙을 확률"*인데,
> 전개 장면은 이미 **내가 그 장면을 만드는 사람으로 뽑힌 뒤**예요. 몫을 또 곱하면
> 주인공 지명을 두 번 세는 셈입니다.
>
> **전개 장면의 정의가 "만드는 장면"이니, 성공하면 도움이 붙습니다.**
> 그러면 두 갈래가 같은 자를 씁니다 —
>
> ```
> 카드(내가 전개 주인공)   P(내 도움) = autoP(me)   ← §2-6 개정으로 정의상 같아졌습니다
> 자동(내가 전개 주인공)   P(내 도움) = FIN × atkW × sc(me) = autoP(me)
> ```
>
> **§2-6이 카드의 중심을 `autoP`로 넘겼으므로 `FIN`을 손댈 필요가 없습니다.**
> (개정 전에는 `succ(70,0.5) = 0.46` vs `0.884 × 0.5 = 0.442`로 4% 어긋났어요.)
>
> **동료가 전개 장면의 주인공이면 내 도움은 없습니다** — 그 동료가 가져갑니다.
> engineer가 §2-8에서 고친 *"우리 팀 동료도 도움을 받는다"*와 정확히 같은 방향이에요.
>
> **`ASSIST_P2`는 폐기가 아니라 자리를 옮깁니다** — 결정 장면의 골에 도움자를 붙이는
> 확률로. 그래야 **리그 전체 도움 ÷ 리그 전체 골 ≈ 0.75**라는 축구다운 비율이 섭니다.

> 🔴 **`a` 무게로 도움자를 지명할 때 현행 `splitMine`의 도움 몫 식
> (`ASSIST_W × (overall/70)^1.2 × 자리결`)을 쓰지 마세요.**
> 그 식에는 **패스 스탯이 없습니다.** inspector가 라이브에서 확인한 결함이에요 —
> 미드필더가 주 스탯(패스)을 특화하면 종합이 덜 올라 **축이 오히려 줄어듭니다(×0.978).
> 키울수록 손해예요.**
>
> v2의 `blend`(포지션별 주 스탯 0.60 가중)를 쓰면 **패스를 올린 만큼 전개 카드의
> 주인공이 될 확률이 직접 오릅니다.** ①이 구조적으로 풀려요.
> 도움자 지명도 같은 `w_a(i) / Σ w_a(i)` 비율을 씁니다.
> 같은 이유로 `sc(x)`의 `abilityOf(x)`도 **종합이 아니라 그 카드 종류의 `blend`**입니다.

### 2-6. 미니게임 성공률 — **중심은 자동 확률, `succ`는 폭만 정합니다**

> ### 🔴 2026-08-28 판정 (inspector F4 · engineer §4-⑤) — 두 문제가 한 뿌리였습니다
> `succ` 표가 **성공률의 중심점**을 독립적으로 정하는 한, 카드 갈래와 자동 갈래는
> **반드시 어긋납니다.** 실제로 두 곳에서 터졌어요 —
> 🅰️ 전개 카드의 도움이 4~6배(engineer §4-⑤) · 🧱 수비 카드의 실점이 능력치 150에서
> −9.8%(inspector F4, `outcome()`의 clamp가 `miss`를 자름).
>
> **중심을 자동 확률에 넘기고, `succ`는 조작이 흔드는 폭만 맡습니다.**

```js
// 한 카드의 "사건이 일어날 확률" — 카드 종류와 무관하게 같은 형태
P(사건 | 카드) = clamp( autoP(me) + 2*half(a)*(s - 0.5), 0, 1 );

  autoP(me) = 그 장면을 자동으로 굴렸을 때의 확률 (§2-5)
              ⚽ 결정  → FIN × atkW × sc(me)          (골)
              🅰️ 전개  → FIN × atkW × sc(me)          (골 + 내 도움)
              🧱 수비  → 1 − pConcede(me)             (막을 확률)
  half(a)   = 선형보간(40 → 0.17, 80 → 0.19, 120 → 0.20)
  s         = 조작 숙련도 ∈ [0, 1] (실제 플레이에서는 판정 결과가 s를 대신합니다)
```

**`s = 0.5`에서 `P(사건) = autoP(me)`입니다 — 중립이 정의상, 모든 능력치에서 성립합니다.**

| | 이전 (`mid(a)` 독립) | **개정 (`autoP` 중심)** |
|---|---|---|
| 중립 | 능력치 70에서만 우연히 맞음 | **모든 능력치에서 정의상 성립** |
| 🧱 수비 clamp | 능력치 150에서 −9.8% | **안 걸림** (150에서 `0.737 + 0.20 = 0.937 < 1`) |
| 🅰️ 전개 도움 | 4~6배 어긋남 | 맞음 |
| 조작 체감 | `±half(a)` | **`±half(a)` 그대로** |
| 검사 10번 밴드 | ±3% | 🔴 **±1%로 조입니다** — 이제 남는 차이는 몬테카를로 잡음뿐이에요 |

> **`mid(a)` 표는 폐기합니다.** `autoP(me)`가 그 자리를 대신해요.
> 그리고 **balancer가 이미 맞춰 놓은 것을 정의로 승격하는 것**이라 계수가 안 움직입니다 —
> `FIN 0.884`·`CON 1.111`이 `s = 0.5`의 `succ`에 맞춰 역산된 값이었어요.
>
> **원칙 ⑥은 오히려 더 잘 지켜집니다.** `autoP`가 능력치를 정직하게 타므로
> 조작 폭(`±0.17~0.20`)이 능력치 폭보다 작으면 역전이 안 나요.
> 검증은 여전히 커리어 단위로 합니다 (§12 실측 2-a).

**미니게임 결과 → 카드 결과**

| 판정 | ⚽ 결정 | 🅰️ 전개 | 🧱 수비 |
|---|---|---|---|
| `perfect` | 내 골 | 동료 골 + **내 도움** | 실점 안 함 |
| `ok` | 슛 시도 (기록 없음) | **무위** (연출만 다름) | 실점 안 함 |
| `miss` | 무위 | 무위 | **실점** |

**`P(사건)`이 곧 위 표의 사건 확률입니다.**

| 카드 | `P(사건)`이 무엇인가 | 나머지 |
|---|---|---|
| ⚽ 결정 | `perfect` = 내 골 | `ok`/`miss` 배분은 **연출 몫** (둘 다 기록이 안 남아요) |
| 🅰️ 전개 | `perfect` = 동료 골 + 내 도움 | `ok`/`miss` = **둘 다 무위**. 🔴 **`ok`가 골을 주면 안 됩니다** — 자동 갈래에서 *골*과 *내 도움*은 **같은 사건**이라, `ok`가 골을 주면 도움 중립은 맞아도 **골 중립이 깨집니다** |
| 🧱 수비 | **`perfect + ok` = 막음** · `miss` = 실점 | 막은 것 중 `perfect`(🛡️ 차단 기록) 비율은 판정 품질이 정합니다 |

> 🧱 수비만 `P(사건)`이 **`1 − miss`**인 것에 주의하세요. `perfect`와 `ok`가 결과가 같아서
> (둘 다 실점 안 함) **중립이 걸리는 자리는 `miss`**입니다.
> `outcome()`이 `miss`를 `1 − perfect`로 clamp하면 그 자리가 깨집니다 (inspector F4).

> **이 표는 지킵니다.** *"내가 킬패스를 성공하면 도움"*은 게임의 약속이고,
> 성공했는데 도움이 확률로 날아가면 원칙 ①(화면의 기대 ↔ 메커닉)을 정면으로 어깁니다.
> **중립은 표를 고쳐서가 아니라 자동 갈래를 고쳐서 지킵니다** (§2-5).

### 5-1. 카드가 열릴 때 **무엇이 걸렸는지 첫 줄에 반드시 밝힙니다**

같은 미니게임이 두 종류로 열리므로(🏃 돌파는 결정에도 전개에도) 여기가 원칙 ①의 자리입니다.

```
⚽ 결정  "🔥 골문 앞! 이걸 넣으면 동점입니다"
🅰️ 전개  "🎯 동료가 뒷공간으로 뛰어요 — 찔러 주세요"
```

### 5-3. ❌ "이기고 있으면 수비 카드가 **더 열린다**"를 약속하지 마세요

**산식에 그 항이 없습니다.** `SCENE_ATK`가 스코어를 안 봐서 상대 공격 장면의 **수 자체는
스코어와 무관**합니다. 실제로 일어나는 것은 이것뿐이에요 —

| 상황 | 실제로 | 화면이 말해도 되는 것 |
|---|---|---|
| 뒤지고 있음 | `urgency`가 `pBig`를 올려 **결정 카드가 늘고 전개가 줄어듭니다** | ✅ "따라가야 합니다 — 기회가 더 옵니다" |
| 앞서고 있음 | `behind = 0`이라 결정 카드가 안 늘어납니다. **수비 카드의 비중이 상대적으로 오를 뿐** | ❌ "지켜야 하니 수비 상황이 늘어납니다" |
| 3점 차 이상 | 카드가 6장에서 끊깁니다 | ✅ "이미 승부가 기울었어요" |

**정확한 서술**: *"수비수·CDM은 스코어와 무관하게 경기 내내 일정하게 개입합니다"*.
이게 참이고, 12번 §1-4에서 제가 *"이기고 있을 때도 할 일이 있다 — 그때가 주무대"*라고
쓴 것은 **절반만 맞았습니다.** 앞부분(할 일이 있다)은 참이고 뒷부분(주무대)은 거짓이에요.

> **왜 산식을 고치지 않고 서술을 고치나** — `SCENE_ATK`에 스코어를 물리면
> 새 계수가 하나 늘고 **곡선을 다시 재야 합니다.** 지금 곡선은 다섯 점 전부 밴드 안이에요.
> 그리고 **값이 0인 배선은 요청하지 않은 미래 대비 코드**입니다.
> **2차 후보로 남깁니다** — 형태는 §12-3에 적어 뒀어요. 리드하는 팀이 내려앉는 건
> 축구적으로 자명해서 언젠가는 넣을 값어치가 있습니다.

## 8. 포지션 · 주발 · 전환

### 8-1. 윙어를 **깊게** 합니다 (세게가 아니라)

이름이 "더 윙어 II"인데 윙어가 4개 중 하나입니다. **현행과 같은 구조라 새 문제는
아니지만**, 현행에서 **윙어가 가장 얕은 게 문제**예요 — 자리가 LW/RW 둘뿐인데
미드필더는 넷, 수비수는 셋입니다.

| | 윙어 | 다른 셋 |
|---|---|---|
| **세부 자리** | **4개** — LW · RW · **인버티드 LW** · **인버티드 RW** | 각 +1 (fw 폴스나인 / mf 레지스타 / df 리베로) |
| 전용 미니게임 | 🏃 컷인 돌파 | 각 1종 |
| 자리 전용 금특 (2차) | 2종 | 각 1종 |
| **기대 산출 · 자리 가중 평균** | **같음 · 1** | **같음 · 1** |

**인버티드 자리가 주발과 맞물립니다** — 반대발 윙어(왼발잡이가 RW)는 **골 ↑ 도움 ↓**,
전통 윙어는 **도움 ↑ 골 ↓**. 넷의 평균은 여전히 1이에요.

⚠️ 새 자리를 `POS_SLOTS`에 넣으면 **정규화 IIFE(`squad.js:41-74`)가 자동으로 다시
정규화**합니다. 자리표만 넣으면 평균 1이 지켜져요.

### 8-2. 🦶 주발 — 셋 다 켭니다

| | 무엇 | 값 |
|---|---|---|
| ① 자리 가중 | 왼발잡이가 왼쪽 자리를 받을 확률 | `FOOT_FIT` 0.04 → **0.10** |
| ② 골·도움 배수 | 약발이 높으면 기여가 큼 | `1 + (약발 − 5) × 0.012` |
| ③ 판정 창 | 주발 쪽 코스가 넓음 | 주발 **+25%** / 약발 **−25%** |

**②는 화면에 안 보이는 효과입니다. 그래서 약발을 화면의 1급 시민으로 올립니다** (원칙 ③):

| 어디 | 무엇 |
|---|---|

| 순간 카드 | 약발 쪽 코스로 성공하면 `🦶 약발로 마무리!` 피드 한 줄 |
| 훈련 결과 | `🦶 약발 5 → 6 승급!` 카드 |

**약발 라벨**: 2 못 씀 / 3 서툼 / 4 약간 / 5 보통 / 6 좋음 / 7 **양발**

**손잡이 — 「약발 훈련」을 1차에 넣습니다.** ⚠️ **훈련 총량은 늘리지 않아요** —
새 슬롯이 아니라 **기존 훈련 슬롯 안의 선택지 하나**입니다. 총량이 늘면 성장 곡선이
통째로 움직입니다(백로그의 판단 그대로).

**3중 중립 검증** (§12 실측 4): 약발 5 · 가운데 자리 · 좌우 균등에서 **정확히 1.000**.

### 9-2. 규칙 여섯 — 이게 표보다 중요합니다

1. **마이그레이션 함수를 만들지 않습니다.** 새 필드는 읽는 쪽에서 기본값을.
   ```js
   const rd = (v, d) => (v == null ? d : v);
   ```
2. **`schemaVersion` 필드를 두지 않습니다.** 버전 번호가 있으면 반드시 마이그레이션
   유혹이 생기고, 그 함수가 옛 세이브를 부수는 첫 번째 경로가 됩니다.
3. **`id`는 영원히 안 바꿉니다.** 성장타입·성향·특능·결함 전부 문자열 `id`예요.
   순서가 필요하면 `order`/`tier` 같은 새 필드를 더합니다
   (축구에서 `id`로 순서를 판단해 사고가 났습니다).
4. **가중 카운터는 옛 카운터를 이어받습니다.**
   ```js
   S.career.mvpW = (S.career.mvpW != null ? S.career.mvpW : S.career.mvp) + prestige;
   ```
5. **배열은 `|| []`, 객체는 `|| {}`.**
6. 🔴 **키로 접근하는 표는 없는 키를 반드시 대비합니다.**
   ```js
   const allStat = 평균(존재하는 값들);
   const st = (k) => (S.stats[k] == null ? allStat : S.stats[k]);
   ```
   **`|| 0`이나 `?? 0`을 쓰지 마세요.** 0으로 채우면 종합이 내려가 그 선수가 갑자기
   약해집니다. **나머지 평균으로 채우면 `(합 + 평균) ÷ (n+1) = 평균`이라 종합이
   소수점까지 안 흔들려요** — ⚡ 스피드 추가 때 검증된 방법입니다.
   적용 대상: `S.stats` · `S.talents` · `S.body` · 앞으로 추가될 모든 키-값 표.

## 10. 시드 주입 창구 스펙 (engineer · inspector)

**점진 확정은 매 경기 결과가 다릅니다.** 고정 시드가 없으면 회귀 검사가 표본 수로
버텨야 하고, 그러면 느립니다.

### 10-1. 요구사항

```js
// ⚠️ 바깥 스코프에 둡니다. 함수 안에 두면 return { _t: … }에서 안 보여요
// (컴백 컨셉 구현에서 정정한 것 — 계획이 FANDOM_CAP 근처를 지목했는데 그 자리는
//  playShow() 안이라 바깥에서 안 보였습니다)

let _rng = Math.random;
const rnd = () => _rng();                 // 🔒 엔진의 모든 난수가 이 하나를 지나야 합니다
const rand = (a, b) => a + rnd() * (b - a);
const randInt = (a, b) => Math.floor(rand(a, b + 1));
const pick = (arr) => arr[Math.floor(rnd() * arr.length)];
```

**`Math.random`을 전역으로 갈아치우지 마세요.** 다른 모듈(`timing.js`·`cloud.js`)이
영향을 받습니다.

### 10-2. `_t` 창구

```js
return {
  /* … 게임 API … */
  _t: {
    seed(n)   { _rng = mulberry32(n >>> 0); },   // 32bit PRNG. 결정론적
    unseed()  { _rng = Math.random; },
```

### 10-3. 🚨 검사가 `_t.K`에서 문턱을 읽으면 안 됩니다

#### (2) `LEAD_TILT` (§5-3에서 미룬 것)

리드하는 팀이 내려앉는 건 축구적으로 자명해서 언젠가는 넣을 값어치가 있습니다.
**형태는 이미 정해 뒀습니다** — 곡선을 다시 재야 해서 1차에는 안 넣어요.

```js
lead = clamp(myScore - oppScore, -2, +2);
tilt = 1 - LEAD_TILT * lead * (k / N);      // 앞설수록·후반일수록 우리 공격 장면이 줄어듦
p(우리 공격) ∝ atkW * tilt;
p(상대 공격) ∝ defW / tilt;                 // 총 장면 수(SCENE_ATK)는 고정 — 비율만 이동
```

`LEAD_TILT = 0.12` 제안. **중립(0-0)에서 `tilt = 1`이라 기댓값이 불변**인 게 이 형태의 장점입니다.
