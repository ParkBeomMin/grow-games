### 손잡이 — **표를 셋으로 나눴습니다** (설계 §4-1 · 원칙 ⑨)

```js
const BLK      = { tellHi, tellLo, hiP, favor };   // 1단계 읽기 신호 (그대로)
const BLK_RUN  = { mark: 70, speed: [58, 74] };    // 2단계 무대 (트랙 %, %/초)
const BLK_WIN  = 14.2;                             // 📏 평균을 붙드는 **종속값**
const BLK_READ = { exact: 1.00, near: 0.45, opp: 0.15 };  // 🎯 읽기 대 손의 **비중 손잡이**
```

`BLK_WIN`의 단위는 **트랙 폭의 %**예요 (`CUT.win`과 같은 자). 설계 §4-1은 비율 0.30으로 적었는데,
`sBar`가 %로 재는 나머지 셋과 같은 자를 쓰려고 %로 두고 주석에 밝혔습니다.

### 이중 탭 (설계 §10)

1단계 버튼 셋 → 2단계 버튼 하나라 **가운데가 정확히 겹칩니다.** 2단계에 **자기 `gate`**를 새로 주고,
1단계 탭이 `pointerdown`으로 왔으면 닫아 뒀어요 — 준비 화면 → 본 게임과 같은 형태입니다.

`.w2m-block` → `.w2m-block2`로 **클래스를 갈아 끼웁니다.** `style.css`가
*"⑥ `.w2m-block`에는 움직이는 것을 하나도 넣지 마세요"*를 지키고 있어서, 2단계가 그 선택자에 걸리면 안 돼요.

| 되돌린 것 | 결과 |

| ① `gate2.shut = !!viaPointer` → `false` (이중 탭 방어 제거) | ❌ 빨간불 |

| ④ `BLK_READ`를 `{1, 1, 1}`로 (판정 창이 읽기를 안 탐) | ❌ 빨간불 (읽기 값어치 2.0%p → −0.1%p) |

> 🔴 **①은 처음에 안 잡혔습니다.** 이 저장소의 기존 `press()`들은 세 이벤트를 **같은 요소**에
> 보내는데, 실제 브라우저는 손 뗄 때 `click`을 **「그 지점에 지금 있는 요소」**로 보냅니다.
> 1단계 버튼은 이미 사라졌으니 jsdom에서는 그 경로가 아예 재현이 안 돼요.
> 🔧 브라우저와 같은 자리 바꾸기를 손으로 해 줬습니다 — `pointerdown`/`up`은 옛 버튼에,
> `click`은 **새로 생긴 🛡️ 막기**에. 그러고 나서야 ①이 빨간불이 됐습니다.
>
> 🔴 **두 번째로 안 잡혔던 것**: 판정을 `cb` 호출로 재면 `ender`가 620ms 뒤에 부르는 탓에

## 5. 🔴 되돌려 묻습니다 (grow-designer)

### ① `BLK_READ`는 **숙련도 폭을 못 정합니다** — 설계 §4-1의 이름과 실제가 다릅니다

설계는 `BLK_READ`를 *"폭을 정하는 손잡이"*로 적었는데, 실측에서 **거의 안 움직입니다.**
평균을 0.510에 붙들어 둔 채 `(near, opp)`를 훑었어요:

| near / opp | BLK_WIN | 숙련도 폭 (A) | 읽기 값어치 |
|---|---|---|---|
| 0.65 / 0.35 | 10.5 | 14.6%p | — |
| **0.45 / 0.15** ← 설계값 | **14.2** | **13.2%p** | 2.1%p |
| 0.26 / 0.08 | 20.4 | 12.1%p | 3.0%p |
| 0.06 / 0.00 (사실상 옛 계단) | 70.5 | 11.0%p | 4.6%p |

**끝에서 끝까지 훑어도 폭은 14.6 → 11.0%p뿐입니다.** 폭을 만드는 건 **손(σt)**이에요 —
읽기만 흔들면 **1.2%p**, 손만 흔들면 **12.3%p**입니다.

🔑 **왜 그런가**: 3택 읽기는 **베이즈 최적으로 읽어도 정타율이 51%**입니다(찍기 33%).
읽기 실력이 벌 수 있는 폭이 **18%p뿐**이라 구조적 상한이에요. 옛 판이 2.0%p였던 것도 같은 이유입니다.

> ★ **`BLK_READ`가 정하는 것은 「읽기 대 손의 비중」**입니다. 설계 §4-1의 두 번째 문장
> (*"키우면 읽기 게임이 되고 줄이면 타이밍 게임"*)은 맞고, 첫 문장(*"숙련도 폭이 여기서 나와요"*)이
> 안 맞아요. 🔴 **주석을 제 판단으로 고쳐 쓰지 않고 설계값을 그대로 넣었습니다.**

### ② 🔴 **읽기의 값어치가 5.4%p → 2.0%p로 희석됐습니다** — 계수로 못 되돌립니다

손을 🙂 평균으로 고정하고 **읽기 전략만** 바꿔 봤습니다:

| 전략 | 옛 E[s] | 새 E[s] |
|---|---|---|
| 🎲 찍기 | 0.435 | 0.481 |
| 👀 몸 방향만 | 0.500 | 0.507 |
| 🔎 겹쳐 읽기 | 0.578 | 0.533 |
| **겹쳐 − 찍기** | **0.143 (5.4%p)** | **0.052 (2.0%p)** |

**손이라는 둘째 층이 생기면 첫째 층의 한계 값어치는 반드시 줄어듭니다.**
`BLK_READ`를 극단(0.06 / 0.00)까지 밀어도 **4.6%p까지밖에** 못 올라가요 —
정타를 읽어도 손이 σt 70ms면 `E[s|정확]`이 0.72라 1.0을 못 채우니까요.

> 🟢 **판 하나 안에서는** 읽기가 확실히 보입니다(0.719 vs 0.175 · §3-3).
> 🔴 **전략으로서는** 읽기의 값어치가 옛 판의 37%로 줄었어요.
> ⚠️ 설계 §3이 *"3택 읽기를 살립니다 — 정교한 설계라 버리면 아깝습니다"*라고 했는데,
> **살아는 있지만 값어치는 3분의 1**입니다. 이게 받아들일 만한 값인지는 **설계 판단**이라
> 제가 안 정했습니다. 손잡이는 `BLK_READ` 한 줄이에요.

### ③ 🟡 겨냥 모델 A만 13.4%p — 밴드를 1.4%p 넘습니다

designer §4-2가 *"①은 추정이라 balancer 19(포지션별 `defend` 빈도)가 먼저"*라고 적어 뒀고,
**그 실측이 아직 없습니다.** 그래서 설계값을 그대로 두고 표만 넘깁니다 —
빈도가 고르면 12%p 쪽이니 A까지 포함해도 거의 닿아요. 좁혀야 하면 위 표의
`(0.26, 0.08)` 줄이 A를 12.1%p로 내리고, 그 대가로 **반대로 읽으면 창이 ±1.0%(≈15ms)**가 되어
*"발을 뻗어 걷어냈어요"*가 사실상 사라집니다(원칙 ③).

     **손 뗀 지점의 새 요소**로 보냅니다. 준비 화면 → 본 게임의 `gate`도 **같은 이유로 지금 안 재고 있어요.**
     재현법은 `scratchpad/eng-blk/dom-check.js` 맨 아래에 있습니다.
  2. **판정이 났는지를 `cb`로 재면 안 됩니다** — `ender`가 620ms 뒤에 부릅니다.
     곧바로 붙는 `.w2m-hit` / `button[disabled]`로 보세요. `cb`로 재면 **변이해도 초록불**이에요.
