## 2. 🔴 가장 중요한 판단 — **미니게임이 판정을 만들지 않습니다**

인터페이스는 요청대로 `fn(container, opts, cb)` → `cb("perfect"|"ok"|"miss")`입니다.
다만 **판정을 만드는 주체를 엔진으로 뒀습니다.**

```js
// career.js
mini(slot, { kind, moment, condition, foot: mainFoot(),
             judge: (s) => m.judgeFor(s) },        // ← s(0~1)를 엔진에 되돌려 물어요
     (judge) => { m.resolve(judge); draw(card); });
```

```js
// engine.js — 새로 뺀 자리
function judgeAt(kind, s) {
  const ab = abilityOf(me);
  const autoP = kind === "defend" ? 1 - pConcede(defW, ab) : pFinish(atkW, ab);
  return outcome(kind, cardP(autoP, ab, clamp(s, 0, 1)));
}
const autoJudge = (kind) => judgeAt(kind, _skill == null ? 0.5 : _skill);
```

**왜 이렇게 했나** — §2-6의 산식이 이렇습니다.

```
P(사건 | 카드) = clamp( autoP(me) + 2*half(a)*(s − 0.5), 0, 1 )
```

`autoP`는 **그 경기의 전력(atkW·defW)과 내 능력치**에서 나오는 값이라 미니게임이 알 수
없어요. 미니게임이 제 손으로 `perfect/ok/miss`를 만들면 그 중심이 `autoP`와 무관해지고,
**카드 갈래가 자동 갈래와 어긋납니다** — §2-6 개정이 고친 바로 그 자리입니다
(🅰️ 전개 도움 4~6배 · 🧱 수비 실점 능력치 150에서 −9.8%).

**미니게임이 내는 것은 조작 성공도 `s` ∈ [0,1] 하나뿐입니다.**
`autoJudge`(자동 진행 · balancer의 `_t.skill`)와 사람 조작이 **같은 함수 `judgeAt`을 지나가요.**
`s = 0.5`에서 중립이 정의상 성립한다는 §2-6의 약속이 배선으로 강제됩니다.

`cb`는 `(judge, { s, moment, weak })`로 부릅니다 — 둘째 인자는 검사·연출용이고
career.js는 안 씁니다.

## 3. 🔴 되돌려 묻는 것 — **능력치를 판정 창에 넣지 않았습니다**

지시문에 *"능력치는 판정 창(관용도)을 넓히고, 조작은 `s`를 정합니다"*가 있었습니다.
**넣지 않았습니다.** 넣으면 같은 문단의 다음 문장(*"balancer가 잡은 곡선이 안 흔들립니다"*)이
깨지기 때문입니다.

| 능력치가 결과에 실리는 경로 | 어디 |
|---|---|
| ① 카드 확률의 **중심** | `autoP = FIN × atkW × sc(me)` — `sc`가 `succ(a, 0.5)/succ(70, 0.5)` |
| ② 조작이 흔드는 **폭** | `2 × half(a)` — 0.17(40) → 0.20(120) |
| ③ ~~판정 창~~ | **안 넣었습니다** |

③까지 넣으면 능력치가 높을수록 `E[s] > 0.5`가 되어 **모든 능력치에서 `s = 0.5`가 중립**이라는
§2-6의 정의가 깨집니다. balancer는 `_t.skill = 0.5`(능력치와 무관한 상수)로 곡선을 쟀으니,
실제 플레이가 능력치마다 다른 `s`를 내면 그 곡선이 통째로 움직여요.

설계 문서도 같은 쪽입니다 — **§4-5의 판정 창 표에는 🦶 주발과 🫀 컨디션만 있고 능력치가
없습니다.** 키·체격은 2차로 미뤄져 있고요.

현행 상용의 `miniZone(stat)`(`winger2/game.js:1889`)이 능력치를 창에 넣는 건 맞지만,
그건 **`autoP`가 능력치를 안 타던 옛 구조**에서 잰 값입니다. 원칙 ⑧ 그대로 —
*"계수표만 보지 말고, 그 계수를 잰 모델 코드까지"*. 표는 닮았는데 모델이 다릅니다.

> **판단이 필요하면 되돌려 주세요.** 켜는 건 `winMul()` 한 줄이지만, 켜는 순간
> **§12 실측 2-a(커리어 20시즌 중립)를 다시 재야 합니다.**

## 4. 4종

전부 준비 화면(▶️ 시작)을 거칩니다. 처음 3번은 전문, 그 뒤엔 한 줄 —
`grow-mech-ready` 열쇠를 야구·아이돌과 나눠 쓰되 이름이 `w2-`로 시작해 안 겹칩니다.
첫 줄에 **무엇이 걸렸는지**(⚽ 결정 / 🅰️ 전개 / 🧱 수비)를 반드시 밝혀요 (§5-1).

### 🏃 컷인 돌파 — 조준 + 타이밍 (wg · fw)

수비수 둘 사이의 **갭이 좌우로 흐르고**, 코스 칸이 둘입니다.
갭이 코스 칸에 왔을 때 그 코스 버튼을 눌러요. **조준과 타이밍이 한 번의 누르기**에 들어갑니다.
🦶 **주발 쪽 칸이 눈에 띄게 넓게 그려집니다** — 그려진 폭이 곧 판정 창이에요.

`s = 1 − |갭 위치 − 코스 중심| / (CUT.win × 창배수)`

### 🥅 1대1 마무리 — 조준 (fw · wg)

키퍼가 달려나와 각을 좁혀요. **골문에서 넣고 싶은 지점을 직접 누릅니다**(방향 버튼이 아니라
좌표 조준이에요 — 3택 버튼으로 만들면 🧱 차단과 화면 문법이 겹칩니다).
기다릴수록 남는 틈이 줄어요. 🦶 골문의 절반이 **색으로 나뉘어** 주발 쪽 판정이 넓습니다.

`s = 1 − max(0, ONE.need − 여유) / (ONE.need × 창배수)` · 키퍼 몸 안이면 0

### 🎯 킬패스 — 조준 + 타이밍 (mf · wg · fw)

동료 셋이 서로 다른 속도로 오프사이드 라인을 향해 뜁니다.
라인을 **넘기 직전**에 그 동료 버튼을 누르면 최고예요. 넘은 동료는 버튼이 잠깁니다.
🦶 주발은 안 걸려요 (§4-5가 1·2번에만 걸었습니다).

`s = 1 − 라인까지 남은 거리 / (KP.win × 창배수)` · 넘었으면 0

### 🧱 차단 — 읽기 (df · mf/CDM)

`beta/soccer/cup.js`의 승부차기 문법 그대로 — **한 줄 힌트 + 방향 버튼 셋.**
**움직이는 것이 하나도 없습니다.** rAF도, 타이머도, 재는 숫자도 없어요.
1초에 고르든 10초에 고르든 결과가 같습니다.

`s`: 정확 1 · 인접(가운데 ↔ 좌/우) `BLK.part` · 정반대 0

> ### 🔴 여기서 한 번 갈아엎었습니다 — 실측이 잡았어요
>
> 처음엔 신호를 둘(**주발** + **몸 방향**)로 두고 *"겹쳐 읽어야 위로 올라간다"*고 주석까지
> 썼습니다. **그런데 숙련도를 흔들어도 `E[s]`가 0.540에서 한 걸음도 안 움직였어요.**
>
> 이유: 신호 세기가 하나면 사후확률의 **크기 순서가 판마다 안 바뀝니다.**
> `favor × (1−tell)/2 = 1.6 × 0.275 = 0.44` vs `tell = 0.45` — 늘 몸 방향이 이겨서,
> "겹쳐 읽는 사람"과 "몸 방향만 보는 사람"이 **항상 같은 버튼**을 눌렀습니다.
> 신호가 둘인 척하는 **신호 하나짜리 판**이었어요.
>
> **고친 것**: 몸 방향에 **세기 두 가지**를 붙였습니다.
> - `확실히 틀었어요` → `tellHi(0.58) > favor × (1−tellHi)/2 (0.336)` → **몸 방향**이 정답
> - `살짝 흔들었어요` → `tellLo(0.24) < favor × (1−tellLo)/2 (0.608)` → **주발 쪽**이 정답
>
> 두 경우의 정답이 **서로 다른 쪽으로 갈라져야** 겹쳐 읽기가 성립합니다.
> 계수는 그 부등호가 양쪽에서 뒤집히도록 잡았고, 파일 주석에 부등호를 적어 뒀어요.
> 고친 뒤 숙련도 반응이 0.505 → 0.557로 살아났습니다.

## 5. 실측 — 네 종의 난이도 (설계 §4-4 ①: ±5%p)

`docs`에 남길 절차: 디스크의 `winger-moment.js`를 `new Function`으로 실어
**그 파일의 `_t.sCut/sOne/sKp/sBlk`를 그대로** 부릅니다 (산식을 베껴 적지 않았어요).
가상 조작자 하나가 네 판을 각각 20만 번 칩니다.

**가상 조작자** — 시간 오차 σ 70ms · 조준 오차 σ 3.5% · 통째로 놓침 3%.
🧱 차단은 조작자를 셋으로 나눕니다 (몸 방향만 60% · 세기까지 겹쳐 읽음 25% · 찍기 15%).

### 컨디션 80 (c\* · condMul 1.000) · 표본 200,000

| 게임 | **E[s]** | s=1.0 | s=0 | [0,.2) | [.2,.4) | [.4,.6) | [.6,.8) | [.8,1] |
|---|---|---|---|---|---|---|---|---|
| 🏃 컷인 돌파 | **0.522** | 0.1% | 13.6% | 21.8 | 12.7 | 18.0 | 22.6 | 24.8 |
| 🥅 1대1 마무리 | **0.522** | 0.0% | 6.4% | 11.6 | 16.8 | 27.2 | 33.8 | 10.7 |
| 🎯 킬패스 | **0.521** | 0.1% | 16.2% | 19.5 | 11.4 | 21.4 | 27.6 | 20.2 |
| 🧱 차단 | **0.537** | 46.1% | 22.1% | 22.1 | 31.8 | 0.0 | 0.0 | 46.1 |

**E[s] 폭 0.017 → perfect 비율 폭 ≈ 0.6%p.** 기준 ±5%p 안입니다. ✅

> **변환**: `perfect` 비율은 `s`에 **선형**이에요 (`cardP = autoP + 2·half(a)·(s−0.5)`,
> `outcome`은 그 확률을 그대로 굴립니다). 그래서
> **Δperfect = 2 × half(a) × ΔE[s]** 이고, `half(70) = 0.19`이므로
> **±5%p ⇔ ΔE[s] 0.132**입니다. 지금 폭은 그 8분의 1이에요.

판정에는 한 번도 안 들어가요. 같은 `moment`면 `s`의 분포가 카드 종류와 무관하게 같습니다.

### 🟠 실측에서 나온 것 — 🧱 차단만 컨디션을 안 탑니다

컨디션은 **판정 창**에 걸리는데(§2-7), 읽기 게임에는 판정 창이 없습니다.
그래서 컨디션 60에서 다른 셋은 −0.02 내려가는데 차단만 0.537 그대로예요.

- 폭이 **1.6%p**라 ±5%p 밴드는 안 넘습니다. **1차를 막지 않아요.**
- 다만 §2-7이 *"원칙 ③은 여기(판정 창) 하나로 지켜집니다"*라고 적었는데,
  **수비수는 컨디션의 손잡이가 하나도 없습니다** (`pBig`는 우리 공격 장면에만 걸려요).
- 손잡이를 만들려면 `BLK.tellHi/tellLo`를 컨디션으로 흔드는 게 자연스러운데
  (*"지쳐서 상대 움직임이 잘 안 보여요"*), **이건 설계 판단이라 제가 안 넣었습니다.**
  → **designer/balancer 판단 요청.**

## 7. ⚠️ pointerdown 이중 탭 — 막은 방법

`post-stage.js`와 **같은 모양**을 복제했습니다 (두 파일이 같은 사고를 겪었어요).

- `onTap(el, fn, gate)` — `pointerdown` 뒤 700ms 안의 `click`은 **같은 요소 안의 메아리**로 버림
- `newGate()` — ▶️ 시작이 `pointerdown`이면 문을 잠그고 게임에 넘김.
  **손을 뗄 때 오는 `click` 한 번은 방금 생긴 게임 버튼이 받는데, 그걸 gate가 삼킵니다.**
  `TAP_ECHO`만으로는 **요소가 바뀌면 무력**해요 — 새 버튼의 `lastPointer`는 초기값이라서요.
- `click`으로 시작한 경우(포인터 없는 환경·키보드)에는 잠그지 않습니다 — 잠그면 그 환경의
  첫 입력이 통째로 사라져요.

jsdom에서 **`pointerdown` → `pointerup` → `click` 셋을 다 보내** 확인했습니다:
네 종 모두 준비 화면이 치워지고, **시작 제스처의 꼬리 click이 게임을 안 건드리고**,
`cb`가 **정확히 한 번** 불립니다.
