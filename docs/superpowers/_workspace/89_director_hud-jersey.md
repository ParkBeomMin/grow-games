## 1. ⚽ 공 — 지웠고, **검사가 다시 찾지 않게** 만들었습니다

### 지운 것은 공 하나가 아니라 **배선 하나**였어요

조율자 말씀대로 공은 이미 장식이었습니다(제가 82번에서 🦶를 글자 칩으로 옮기면서
공을 가운데로 밀어냈어요 — 거울이 반 바퀴마다 거짓말을 해서). 지우니 **셋이 같이 사라졌습니다**:

| | 무엇이 사라졌나 |
|---|---|
| ① | `char3d.js`의 **마지막 절대색** `#ffffff` — 이제 이 파일에 색이 **한 개도 없습니다.** 전부 `kit`(= `--kit-*`)에서 와요 |
| ② | `markBall()`이 매 프레임 재서 CSS로 넘기던 `--ball-x` `--ball-w` `--ball-bot` **세 변수**와, 그걸 읽던 `.w2c-stage.is-3d .w2c-foot` 규칙 — **3D와 CSS 사이의 배선 하나** |
| ③ | 구 메시 하나 · 지오메트리 하나 · 재질 둘 (**드로우콜 10 → 9 · 폴리 1,008 → 840 tri**) |

② 덕에 🦶 칩은 이제 **3D가 뜨든 안 뜨든 같은 자리**에 앉습니다. 덜 얽힌 쪽이 맞아요.

### 🔴 검사가 공을 찾지 않게 — **이름이 아니라 형태로** 막았습니다

```
A절이 재는 것의 역사 — 세 번 뒤집혔습니다
 ① 캐릭터판   "공이 주발 쪽인가"        → 방향이 맞다를 지킴
 ② 유니폼판   "공이 어느 쪽도 아닌가"   → 방향을 안 쓴다를 지킴
 ③ 지금       "공이 없나"               → 그 장치가 없다를 지킴
```

`probe()`가 `ball` `ballPct` `ballW` `ballTopPct` `ballBotPct` **다섯 필드를 아예 안 냅니다.**
남겨 두면 검사가 그걸 계속 읽고, **읽는 검사가 있으면 다음 사람이 공을 되살릴 자리**가 생겨요.

대신 `stray` — `shirt` 바깥에 매달린 메시 수 — 를 냅니다.

> 🔒 **변이 검증했습니다.** 공을 `orb`라는 **다른 이름**으로 되살렸더니
> `[A/L]` `[A/R]` **2건 빨간불** (`shirt 바깥 메시 1개`). 이름을 바꿔도 안 빠져나갑니다 —
> 이 저장소가 「폐기는 이름이 아니라 형태」로 한 번 데인 자리라 그렇게 짰어요.

②가 지키던 것(*"좌우로 뜻을 만들지 않는다"*)은 **칩으로 옮겨서 그대로 지킵니다**:
`[A] 왼발판과 오른발판에서 칩의 화면 x가 같다` — 실측 **L 50% · R 50%**.

### 📐 그리고 무대의 **3분의 1이 돌아왔습니다** — 이건 제 판단입니다

공만 지우고 렌더해 봤더니 *"옷이 위쪽에 조그맣게 떠 있는"* 화면이 남았어요.
카메라가 **바닥(y=0)** 을 무대의 80%에 두고 있었는데, 옷자락은 y=0.42라
**아래 33%가 통째로 비어 있었습니다.** 그 자리가 공 자리였거든요.

**바닥이 아니라 옷에 맞춰 잡았습니다** — 옷자락~어깨 위를 채우고 위아래 여유만 둡니다.

| | 전 | 후 |
|---|---|---|
| 유니폼 화면 세로 | (공 자리 포함) | **75.6~75.7%** ✅ |
| 등판 사각형 (390px) | y 17.4~47.9 | **y 26.2~66.7** (세로 30.5 → **40.5%**) |
| 폴리 · 드로우콜 | 1,008 · 10 | **840 · 9** |

> 🔑 **세로 프레이밍이 이제 무대 크기·비율과 무관해졌습니다** (위아래 다 `FIT`에서 옵니다).
> 옷자락의 화면 %가 어느 기기에서나 같아요 — 그래서 🦶 칩 자리를 CSS %로 박아도 안전합니다.
> 공을 매번 재서 넘기던 배선이 필요 없어진 이유예요.

⚠️ 그 대신 **옷자락이 칩 자리까지 내려옵니다.** 예전엔 *"칩이 공을 덮나"*를 쟀는데
이제 덮일 수 있는 건 **옷**이에요. 검사를 그쪽으로 바꿨습니다 —
`probe().shirtBox`(소매 끝까지 포함한 화면 사각형) vs 칩 사각형의 **교차**로 잽니다.
`PAD_B`나 `.w2c-foot { bottom }`을 건드리면 빨간불이에요.

**실측(390px)**: 칩 y87.8~97 · 옷 y6.6~82.3 — **5.5%p 여유**. 320px(무대 176px)에서도 안 겹칩니다.

## 2. 🔑 HUD 유니폼 — **굽지 않았습니다. 더 나은 방법이 있었어요**

조율자 제안은 *"조립대에서 한 번 렌더해 이미지로 굽고(`toDataURL`), HUD는 그 이미지만"* 이었고,
*"더 나은 방법이 있으면 그걸로 하세요"* 라고 열어 주셨습니다. **그걸로 갔습니다.**

### ✅ HUD는 **CSS 유니폼 그 자체를 줄여서** 씁니다 (`transform: scale(.3333)`)

이미 조립대에 **CSS 폴백 유니폼**(`.pc-jersey` — `<i>` 다섯 개 + 글자)이 있었어요.
WebGL이 없을 때 서는 옷인데, 3D와 **같은 `--kit-*` 네 값**을 읽습니다.
그걸 **같은 마크업 그대로** 줄여서 HUD에 놓았습니다.

### 왜 굽지 않았나 — 다섯 가지

| | |
|---|---|
| ① 🔴 | **굽는 쪽이 오히려 three.js를 더 받습니다.** 조립대는 커리어당 한 번뿐이에요 — **이어하기로 들어온 판에는 구울 것이 없습니다.** 그럼 🏠 유스 홈이 44px 그림 한 장을 위해 **691KB를 매 세션 받게** 돼요. 「첫 로딩에 three.js를 받지 않기」가 정확히 거기서 깨집니다 |
| ② | 44px짜리 래스터 한 장에 WebGL 컨텍스트를 여는 값이 너무 큽니다. 그 크기에서 3D 렌더와 CSS 유니폼은 **구분이 안 됩니다** |
| ③ 🏟️ | **팀 색이 생겨도 다시 구울 필요가 없어요.** `--kit-*` 네 변수만 갈면 3D·폴백·HUD가 **한 번에** 갈아입습니다. **캐시 수명주기가 아예 안 생깁니다** — 조율자가 열어 두라고 하신 그 자리가, 구울 때보다 더 깔끔하게 열립니다 |
| ④ | 세이브에 이미지를 넣을 이유가 사라집니다 (`localStorage`·클라우드 동기화 무관) |
| ⑤ | **jsdom에서도 그대로 그려집니다** — 검사 14종이 안 죽어요 |

그리고 결정적으로 — **HUD에서 WebGL이 안 도는 게 「정책」이 아니라 「구조」가 됩니다.**
끄는 걸 한 경로라도 놓칠 일이 없어요. 켤 코드가 없으니까요.

### 🔑 **마크업의 출처는 하나입니다** — 두 벌로 나뉘면 반드시 갈라져요

```js
WingerProspect.jerseyHTML({ name, no, mini, label })   // 👕 유니폼 한 벌의 유일한 출처
WingerProspect.paintJersey(el, S)                      // HUD 한 칸을 칠해요
```

`stageHTML`(조립대 폴백)도 `paintJersey`(HUD)도 **같은 함수**를 부릅니다.
조립대에서 본 옷과 HUD의 옷이 다른 옷이면 *"내 선수"*가 깨져요.

⚠️ `mini`면 **이름을 안 넣습니다.** 0.33배에서 이름은 4px이라 못 읽어요 —
**못 읽는 글자는 정보가 아니라 얼룩**입니다. 번호는 **18px**(390px 기준)이라 읽힙니다.

### 🎨 `--kit-*`를 `.w2c-stage`에서 **`:root`로 올렸습니다**

무대에만 두면 HUD가 못 읽어서 **두 벌의 색이 갈라집니다.** 셋(3D·폴백·HUD)이 같은 네 값을 봐야 해요.
팀 색이 생기면 `document.documentElement.style.setProperty("--kit-body", …)` **네 줄**이면 끝입니다.

## 4. 📏 자리 값 — **390px 세로에서 무엇을 내주고 무엇을 얻었나**

**HUD 전체 높이 (실측 · 픽스처와 실제 진입 경로로 잼)**

| | 전 | 후 | Δ |
|---|---|---|---|
| 🏠 유스 **390px** | 156px | **163px** | **+7px** |
| 💼 프로 **390px** | 195px | **195px** | **+0px** ✅ |
| 🏠 유스 320px | 156px | 176px | +20px |
| 💼 프로 320px | 195px | 214px | +19px |

**390px에서 프로는 한 픽셀도 안 늘었습니다.** 팀 정보 줄이 이미 세 줄이라
왼쪽 여백이 비어 있었어요 — 유니폼이 그 빈 칸에 들어갑니다.
유스는 +7px인데, 이름+소속 두 줄(≈44px)보다 유니폼(50px)이 6px 높아서 나온 값이에요.

**320px에서는 `1년차 1월 · 💰0만` 줄이 아래로 갈라집니다.** 유니폼을 한 치수 줄여
(**36×41**, 번호 15px) +27px → **+20px**로 줄였습니다. 더 줄이면 번호가 10px 밑으로
내려가 못 읽어요 — **그럼 넣을 이유가 없습니다.**

> ⚠️ 💼 **프로 화면 320px에 가로 넘침 25px이 있습니다 — 제 것이 아니에요.**
> HEAD를 그대로 띄워 재 봤고 **전에도 25px**이었습니다. 유니폼을 붙여도 그대로 25px예요.

## 5. 🔴 성능 — **재서 적습니다**

### ⏱️ 프레임 (헤드리스 · HEAD를 별도 포트에 띄워 **같은 브라우저로 번갈아** 잼)

| | 🧬 조립대 | 🏠 유스 홈 | 훈련 10회 뒤 |
|---|---|---|---|
| 전(HEAD) | 60.5fps · 1,008 tri · 10 calls | 61fps | 60.5fps |
| **후** | **60.5fps · 840 tri · 9 calls** | **61fps** | **60.5fps** |
| 전(재측정) | 61fps | 61fps | 60.5fps |
| 후(재측정) | 60.5fps | 61fps | 60.5fps |

**차이가 없습니다.** 그럴 수밖에 없어요 — HUD 유니폼은 `<span>` 여섯 개와
`transform: scale()` 한 번이고, **애니메이션이 하나도 없습니다.**
`transform`은 합성만 다시 하니 저사양에서도 레이아웃·페인트가 안 돕니다.

### 🔥 순간 카드가 도는 화면 — **62fps · WebGL 요청 0회**

```
[H2] ⚽ 경기 화면에 도달                                        screen-stage
[H2] 🔥 순간 카드가 도는 화면에는 **HUD도 유니폼도 없다**        hud:false kit:false
[H2] 🔴 순간 카드가 도는 동안 **WebGL을 요청하지도 않는다**       요청 0 → 0
[H2] ⏱️ 순간 카드 화면이 프레임을 지킨다                        62 frames/s
```

`screen-stage`에는 **원래 `<header class="hud">`가 없습니다.** 그래서 HUD 유니폼이
경기 화면까지 따라올 길이 구조적으로 없어요 — 그래도 **검사가 그걸 지킵니다.**
나중에 누가 경기 화면에 HUD를 붙이면 이 줄이 빨간불이 됩니다.

## 6. 🔴 검사가 초록불인데 아무것도 안 지키고 있었습니다 — **아홉 번째 모양**

이번에 스스로 한 번 속았고, 잡아서 고쳤습니다. **남길 가치가 있는 형태예요.**

**처음 쓴 검사:** `[H] HUD에서 WebGL이 돌지 않는다` = `W2Char.live === false && 3D캔버스 === 0`

**변이 검증:** `renderMain`이 `W2Char.show($("hud-kit"), …)`를 부르도록 **일부러 망가뜨렸습니다.**

### → **초록불이었습니다.**

왜냐면 헤드리스 크로미움이 조립대에서 쓴 컨텍스트를 놓은 **직후에 새 컨텍스트를 안 내줘서**,
3D가 그냥 **실패**하고 CSS로 떨어졌거든요. 즉 검사가 지킨 게 아니라
**환경이 우연히 막아 준 것**이었습니다. 실기기에서는 그 컨텍스트가 나옵니다.

### ✅ 고친 방법 — **성공했는지가 아니라 「달라고 했는지」를 셉니다**

`HTMLCanvasElement.prototype.getContext`를 감싸서 `webgl*` 요청 횟수를 셉니다.
`W2Char.show()`는 무엇보다 먼저 `webglOK()`로 컨텍스트를 만들어 봐요 —
**성공·실패와 무관하게, 기기 성능과도 무관하게** 잡힙니다.

조립대 몫은 정당하니까, **조립대를 떠나기 직전에 눈금을 찍고 그 뒤의 증가분**을 봅니다.

거기에 **자물쇠를 하나 더** 걸었습니다: `is-3d`/`is-flat` 클래스는 `char3d.js`만 붙여요 —
3D가 **실패해서 CSS로 떨어져도 흔적은 남습니다.**

> 🔒 **다시 변이 검증:** 같은 변이로 **4건 빨간불** —
> `요청 2 → 4` (유스 320·390) · `class 표식 "is-flat"` (유스 320·390). 이제 잡힙니다.

**교훈 한 줄:** *"안 일어났다"* 를 재면 **환경이 막아 준 것과 코드가 막은 것을 구분 못 합니다.**

## 7. ♿ `prefers-reduced-motion`

HUD 유니폼은 **애니메이션이 하나도 없어서** reduce에서 잃을 움직임이 없습니다.
그런데 *"움직임이 없으니 볼 것도 없다"*가 아니에요 — 움직임을 끄는 규칙이 실수로
`display: none`이나 `opacity: 0`을 잡으면 **번호가 통째로 사라집니다.**
(조립대에서 실제로 `animation: none`이 `both`의 시작 상태 `opacity: 0`에 갇힌 적이 있어요.)

**그래서 H3절을 따로 뒀습니다** — reduce 판에서 유니폼과 번호가 **그대로 보이는지**를 잽니다.

**실측(390px · reduce)**: `display: block` · `opacity: 1` · 번호 `opacity: 1` · **34.7×18.1px** ·
WebGL 요청 `2 → 2`(유스) `0 → 0`(프로) — **하나도 안 잃습니다.**
