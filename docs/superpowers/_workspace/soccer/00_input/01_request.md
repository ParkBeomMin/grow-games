## 오케스트레이터가 정한 진행 방식 (바꾸려면 근거를 적어 올릴 것)

- **한 설계 안에서 단계를 나눈다: ① A+B → ② C → ③ D.** 큰 밸런스 변경을 겹치지 않는다(백로그의 「둘을 겹치면 어디서 틀어졌는지 못 찾는다」).
  C 는 A 의 이벤트 틀 위에 올라가고(입영 통지·상무 지원이 선택 이벤트다), D 의 서버 최초 기록은 B 의 업적 위에, 영구결번·공유 링크는 기존 `hof` 위에 올라간다
- 단계마다 설계 → 실측(balancer) → 구현(engineer·director) → 검증(inspector) → **사용자 실기기 확인**. 상용 승격(`promote.sh`)은 사용자가 지정한다
- **D 의 Supabase 스키마 변경(표·RPC·정책)은 SQL 파일로 준비만 하고, 운영 DB 적용은 사용자 승인 뒤에 한다**

## 이미 정해진 것 — 뒤집지 말 것

- **리그 이름은 실명**(2026-08-06 사용자 결정, 백로그). 구단·방송·브랜드는 가상. 병역에서 군 팀 이름을 쓸 일이 생기면 실존 구단명(예: 「김천 상무 FC」)이 아니라 가상 또는 기관명으로 — **설계에서 판단 지점으로 올릴 것**
- 저장 데이터는 **마이그레이션하지 않는다** — 새 필드는 읽는 쪽 기본값. `id` 는 안 바꾼다
- 밸런스 수치는 **몬테카를로 실측**으로
- 사용자 문구는 존댓말(`~해요`), 기존 파일 어투
- 공유 파일(`timing.js`·`base.css`·`cloud.js`·`match.js`·`help.js`)은 짧게. 새 기능은 **전용 파일로**
- `hof` 표는 **UPDATE 정책이 없다**(헌액은 INSERT 한 번). 쓰기 문은 비밀번호 확인 RPC 방식(피버·한마디 가리기)이 선례

## 오프사이드에서 가져오지 않는 것

- **문구·사건 구성을 베끼지 않는다.** 구조(선택지·확률 공개·연속 스토리·도감·회고·업적 희귀도·병역 규칙)만 참고한다. 글과 사건은 새로 쓴다
- 구글 로그인·계정 동기화·게시판 댓글 — 이번 범위 밖(사용자가 고른 D 에 없다)
- 반기 단위 일괄 시뮬 — 더 윙어는 이미 월 턴·라운드 진행이 있다
