# 설계 — 🎯 타격 구역 선택 화면 (`beta/rookie/`)

2026-09-06 · **작성: Codex `gpt-6-astra`** · 구현: Claude
요청: *"야구게임 진행될때 시각화해서 보여주고.. 미니게임으로 타자는 어느 구역으로 휘두를지 정하는 게임이랑 휘두르는 타이밍 게임 추가하자"*

> 🔑 아스트라가 요청을 그대로 받지 않고 **세 가지가 이미 있다**고 되물었습니다 —
> 시각화(`diamond.js`) · 타이밍(`MINI_BAT[0]`·`Timing.play`) · **구역 선택(`Timing.duel`의 몸쪽·가운데·바깥쪽)**.
> 구현자가 실물에서 셋 다 확인했습니다 (`game.js:1832`·`1774`·`1893`).

---

**결정: 새 조작 축은 추가하지 않고, 이미 있는 ‘코스 3택’을 공간형 구역 선택 화면으로 바꿉니다. 타이밍과 연속으로 시키지 않습니다.** 기존 판정 분포와 등장 빈도를 그대로 보존하면서, 무엇을 고르는 게임인지 더 잘 보이게 만드는 변경입니다.

파일은 수정하지 않았습니다. 아래 함수명 중 새로 제안하는 것은 ‘신규’로 표시했습니다.

**A. 판단**

| 요청 | 결정 | 코드 근거와 이유 |
|---|---|---|
| 경기 시각화 | **안 만든다 — 기존 유지** | `diamond.js`의 `make()`·`state(pa)`가 주자, 아웃, 투구와 타구를 이미 그립니다. 새 경기장을 만들 필요가 없습니다. |
| 구역 선택 | **있는 걸 고친다** | `game.js`의 `playRandomMini()` 마지막 분기는 이미 `Timing.duel()`에 `["몸쪽", "가운데", "바깥쪽"]`을 전달합니다. 새 축보다 기존 선택의 공간 표현을 개선합니다. |
| 타이밍 | **안 만든다 — 기존 유지** | `MINI_BAT[0]`, `Timing.play()`, 고교의 `beginMoment()`에 이미 있습니다. `miniZone(stat)`도 연결되어 있습니다. |

전제 두 가지는 실제 코드에 맞춰 보정해야 합니다.

- **구역 선택도 이미 있습니다.** `Timing.duel()`은 함정·최적 구역을 정하고 세 구역 중 하나를 고르게 합니다. 가을야구의 `PostStage.mind`·`course`도 별도로 존재합니다.
- **모든 중계가 구조화된 타석 경로인 것은 아닙니다.** `renderGameSim()` 내부 `showFeed()`는 `f.pa`가 있으면 `dia.state(f.pa)`, 없으면 `dia.say(f.text)`를 호출합니다. `beginProMoment()`의 내 타석 결과도 현재는 텍스트 피드입니다. 따라서 저장소 전체가 이미 ‘글 파싱 없음·100% 일치’를 충족한다고 단정할 수 없습니다.

또한 `docs/04_전용-미니게임-선례.md`는 실제로 아이돌 전용 파일의 선례이며 `ok`라고 적혀 있습니다. 이번 인터페이스는 실제 `timing.js`·`post-stage.js`와 사용자 계약에 따라 **`perfect / good / miss`**를 따릅니다.

**B. 구현 설계**

**1. 무엇을 푸는가**

“문장 아래 버튼을 찍는 대신, 타격 구역 그림에서 내가 노릴 코스를 직접 눌러 선택합니다.”

이 변경의 가치는 새 보상이나 난이도가 아니라 **기존 코스 선택을 알아보기 쉽게 만드는 것**입니다. 투구 위치를 보고 반응하는 조준 게임이라고 광고하지 않습니다. 현재 메커닉은 단서를 보고 코스를 선택하는 게임입니다.

**2. 중립성 증명**

비교 대상은 **현재 타자 `duel` 분기**입니다. 다른 미니게임을 이 게임으로 교체하거나 등장 확률을 높이지 않습니다.

현재 `Timing.duel()`의 규칙은 다음과 같습니다.

1. 세 구역 중 함정 하나를 균등하게 뽑습니다.
2. 최적 구역을 뽑되 함정과 같으면 다음 구역으로 옮깁니다.
3. 선택이 함정이면 `miss`, 최적이면 `perfect`, 나머지는 `good`입니다.

단서를 무시하고 균등 무작위 선택을 하면:

| 판정 | 확률 | 기존 배수 |
|---|---:|---:|
| perfect | 1/3 | 1.12 |
| good | 1/3 | 1.00 |
| miss | 1/3 | 0.40 |

따라서:

```text
E[배수] = (1.12 + 1.00 + 0.40) / 3 = 0.84
신규 화면 / 기존 화면 = 0.84 / 0.84 = 1
추가 보정 = 0
```

**중립은 평균 배수를 1로 만드는 것이 아닙니다. 현재의 0.84를 보존하는 것입니다.** 이를 1로 올리면 오히려 기존 대비 약 19.05% 상향입니다.

단서가 나오면 함정을 피하고 나머지 두 곳을 균등하게 고르는 전략도 확인합니다. 단서 확률을 `h`라 하면:

```text
P(perfect) = P(good) = 1/3 + h/6
P(miss) = (1-h)/3
E[배수] = 0.84 + 0.22h
```

기존 `hintChance` 산식도 유지합니다.

```js
clamp((stat - 40) / 80 + (S.condition - 50) / 400, 0, 0.9)
```

| 컨택 / 컨디션 | h | 기존·변경안의 기대 배수 |
|---|---:|---:|
| 40 / 50 | 0 | 0.8400 |
| 90 / 50 | 0.625 | 0.9775 |
| 150 / 50 | 0.9 | 1.0380 |

읽기 전용으로 기존 소스의 추첨식과 배수식을 추출해, 조건별 100만 회를 실행했습니다. 단서가 있으면 함정을 피하는 위 전략의 측정값은 각각 **0.840298 / 0.977422 / 1.037979**였습니다. 이는 기존 모델의 확인이며, 아직 없는 새 구현을 검증한 결과는 아닙니다.

더 강한 보존 조건은 다음과 같습니다.

> 같은 난수·같은 선택 구역·같은 제한시간 내 입력이면, 변경 전후 최종 판정이 반드시 같다.

이 조건은 평균뿐 아니라 판정 분포 전체를 보존합니다. `perfect`일 때 비홈런 안타를 2루타로 처리하는 현재 후속 분기도 있으므로, **배수 평균만 같은 설계보다 안전합니다.**

현재 최적 구역 추첨에는 함정과 겹치면 다음 칸으로 옮기는 비대칭이 있습니다. 이번에 이를 ‘공정하게 개선’하지 않습니다. 그 변경도 전략별 확률을 바꿉니다.

**3. 판정 → 결과 배선**

구역과 타이밍을 **한 타석에서 함께 평가하지 않습니다.** 기존처럼 선택된 미니게임 하나가 판정 하나를 반환합니다.

```text
기존 미니게임 추첨
  ├─ 타자 duel → 공간형 코스 선택 → perfect/good/miss
  ├─ bar      → 기존 타이밍     → perfect/good/miss
  └─ 나머지   → 기존 메커닉     → perfect/good/miss

→ 기존 콜백
→ 프로 타석이면 beginProMoment() 내부 doRes(res)
→ 기존 clamp(hitP * mult, 0, 0.95)
→ 기록·득점·중계 처리
```

구역 배수, 추가 안타 추첨, 판정 승급, 두 판정의 평균·최솟값은 넣지 않습니다. `hitP`, `mult`, 홈런 확률도 수정하지 않습니다.

고교 등 다른 호출부는 기존 콜백을 그대로 받습니다. 그 경로까지 프로의 `hitP × mult`를 쓴다고 가정하지 않습니다.

**4. 함수 단위 설계**

변경 범위를 최소화하기 위해 **기존 `Timing.duel()`을 호출하고 야구 전용 화면만 꾸미는 어댑터**를 권합니다.

| 파일 | 구현 지점 |
|---|---|
| 신규 `beta/rookie/bat-zone.js` | `window.RookieBatZone.play(container, opts, cb)` |
| 신규 파일 내부 | `decorateZone(wrap)` — 기존 세 버튼의 공간 배치·설명·접근성 속성 적용 |
| `beta/rookie/game.js` | `playRandomMini()`의 마지막 `duel` 분기에서 타자만 새 어댑터 호출 |
| `beta/rookie/style.css` | `.rookie-bat-zone` 아래 전용 스타일 |
| `beta/rookie/index.html` | `../timing.js` 이후, `game.js` 이전에 `bat-zone.js` 등록 |
| `beta/rookie/sw.js` | `ASSETS`에 `"./bat-zone.js"` 추가, 캐시 버전 갱신 |

신규 공개 인터페이스:

```js
RookieBatZone.play(container, {
  label,
  choices,
  hintChance
}, cb);
```

구현 순서:

1. 전용 호스트 요소를 `container`에 붙입니다.
2. `Timing.duel(host, opts, callback)`을 한 번 호출합니다.
3. 동기적으로 생성된 `.tm-box`에 전용 클래스를 붙이고 화면을 꾸밉니다.
4. 기존 버튼과 `data-i`를 보존합니다. 버튼을 복제하거나 이벤트를 다시 연결하지 않습니다.
5. 기존 콜백이 오면 호스트를 제거하고 `cb(res)`를 한 번 전달합니다.

`Timing.duel()`의 추첨, 제한시간 6초, 결과 표시 500ms, 완료 가드를 그대로 사용합니다. 새 난수·타이머는 필요 없습니다.

`playRandomMini()`에서는 현재 `autoMiniOn()` 조기 반환 다음에 타자 여부로 렌더러만 선택합니다. 투수는 기존 `Timing.duel()`을 호출합니다. 기존 `cb(res, DUEL_BAT)` 형태도 유지합니다.

이 방식은 공유 DOM 클래스에 의존합니다. 필요한 요소가 실제로 생성되는지 검사를 두고, 구조가 바뀌면 검사가 실패하도록 합니다.

**5. 화면과 `diamond.js`의 관계**

모바일 세로 화면의 기존 `#game-moment` 안에 표시합니다.

- 제목: “노릴 코스를 골라요”
- 설명: “구역을 한 번 누르면 선택돼요. 빠르게 누른다고 유리하지 않아요.”
- 기존 단서 문장
- 정적인 타격 구역 사각형: **몸쪽 | 가운데 | 바깥쪽**, 같은 폭의 세 열
- 기존 세 버튼 전체가 각 열의 터치 영역

구역은 최소 높이 72px, 텍스트·테두리·선택 표시를 함께 사용합니다. 색만으로 구분하지 않습니다. 타석 방향 정보가 없으므로 좌타·우타의 실제 시점을 주장하는 선수 그림은 넣지 않습니다.

9분할은 하지 않습니다. 높낮이는 현재 판정 모델에 없으므로 여섯 칸을 추가해도 실제 선택은 늘지 않고 터치만 어려워집니다.

**`diamond.js`에는 구역 선택 결과를 전달하지 않습니다.** 선택한 코스는 의도이며, 실제 투구 위치나 타구 방향을 뜻하지 않습니다. 선택 직후 경기장에 안타·주자·득점을 미리 표시하지 않습니다.

판정 피드백도 “홈런!”이 아니라 “코스 선택 판정: 퍼펙트”처럼 조작 평가임을 명시합니다. 실제 결과는 기존 결과 처리 이후에만 표시합니다.

**6. 자동 진행**

자동 경로는 현재 위치와 호출 횟수를 유지합니다.

- `beginProMoment()`의 프로 타석 자동 진행은 지금처럼 `autoRes(S.stats.contact)`를 바로 호출합니다.
- `playRandomMini()`까지 들어오는 자동 경로는 기존 분기에서 `autoRes(stat)` 후 반환합니다.
- 자동일 때 구역 DOM, 타이머, 선택용 난수를 만들지 않습니다.
- 자동 설정 변경은 기존처럼 다음 미니게임 진입 때 반영합니다. 진행 중인 판을 별도 자동 재판정하지 않습니다.

자동 판정 위에 구역 판정을 추가하면 중립성이 깨지므로 금지합니다.

**7. 엣지 케이스**

| 상황 | 처리 |
|---|---|
| 옛 세이브 | 새 저장 필드 없음. 기존 저장 키와 로드 처리 유지 |
| 가을야구 | `inPostMini()` 조기 분기를 보존하여 `playPostMini()`의 네 종류 유지 |
| 고교 최종 승부처 | `beginMoment()`의 기존 타이밍 유지 |
| 리그 난이도 | 구역 수·제한시간·힌트에 새 리그 보정 없음. 기존 상대 전력 경로 유지 |
| 연속 탭 | 기존 `done` 가드로 콜백 한 번. 별도 재판정 없음 |
| 미선택 | 기존 6초 제한 뒤 `miss`. 기다리기로 성공하는 규칙 없음 |
| 작은 화면·큰 글씨 | 구역 라벨 줄바꿈 허용, 가로 스크롤 없이 세 열 유지 |
| 키보드 | 실제 버튼을 유지하여 Tab·Enter·Space 입력 지원 |
| 오프라인 | 새 스크립트 캐시 등록 및 재접속 없이 진입 확인 |

**폐기된 형태로 돌아가지 않는 이유:** 선택 전 화면에는 날아오는 공도, 스윙 버튼도 없습니다. 정적인 구역을 직접 누르는 것이 행동입니다. 볼을 골라내기 위해 일부러 안 누르는 선택도 없습니다. 공 애니메이션은 기존 경기 결과 표시에서만 사용합니다.

**8. 검사와 변이 검증**

신규 검사 파일은 `tests/rookie/bat-zone-test.js`로 제안합니다.

먼저 무변이 기준선이 통과해야 합니다. 변이는 원본 파일을 덮어쓰지 않고 메모리상의 소스 또는 별도 작업 사본에서 실행합니다.

| 단언 | 반드시 빨간불이어야 하는 변이 |
|---|---|
| 같은 난수·선택이면 기존 duel과 판정 일치 | `miss`를 `good`으로 바꿔 전달 |
| 기존 힌트 확률을 그대로 전달 | `hintChance`를 항상 1로 변경 |
| 새 어댑터는 추가 난수를 소비하지 않음 | 장식용 `Math.random()` 추가 |
| 실제 타자 duel 진입 시 구역 세 칸이 표시됨 | 호출을 기존 `Timing.duel()`로 되돌림 |
| 세 구역의 위치·버튼 인덱스 일치 | 몸쪽·바깥쪽의 `data-i` 교환 |
| 자동 경로에서 UI 호출 0회, 완료 1회 | 자동 조기 반환 제거 |
| 가을야구에서는 새 어댑터 호출 0회 | 가을야구 분기보다 먼저 새 게임 호출 |
| 판정 하나만 기존 결과 처리에 도달 | 콜백을 두 번 전달 |
| 중계·개인 기록의 같은 입력 재생 결과가 변경 전후 일치 | 선택 이벤트에서 안타·득점 추가 |
| 오프라인에서 새 화면 도달 | `ASSETS` 등록 제거 |

DOM 테스트는 자연 추첨을 기다리지 말고 타자 `duel` 분기를 확정적으로 선택합니다. 실제 구역 버튼을 눌렀는지도 단언합니다. 6초 뒤 자동 실패로 끝난 것을 입력 성공으로 세면 안 됩니다.

포인터 테스트는 `pointerdown → pointerup → click` 전체와 연속 탭, 제한시간 직전 입력을 포함합니다.

산식 측정은 기존 `Timing.duel()`의 추첨식, `game.js`의 `hintChance`, `hitP`, `mult`, `autoRes`를 **정규식으로 추출해 실행**합니다. 추출 실패는 통과가 아니라 검사 실행 오류입니다. 새 파일에는 별도 밸런스 산식을 만들지 않습니다.

중계의 100% 일치 검사는 **기존 `say(text)` 경로도 따로 포함**해야 합니다. 거기서 기존 불일치가 나오면 이번 화면 변경의 통과와 분리해 보고해야 하며, 전체 계약을 충족했다고 선언해서는 안 됩니다.

**9. 하지 않기로 한 것**

- **구역 선택 후 타이밍까지 연속 수행:** 짧은 세션을 늘리고 추가 판정 축을 만듭니다.
- **구역 적중 배수:** 기존 `hitP × mult` 뒤에 육성·조작 곱셈을 다시 만듭니다.
- **기존 8종의 추첨 비중 변경:** 화면 개선을 성적 분포 변경과 섞지 않습니다.
- **투구 궤적·볼 판별·기다리기 성공:** 세 번 폐기한 형태를 되살립니다.
- **선택 코스로 실제 타구 방향 결정:** 엔진에 없는 사실을 중계가 만들어냅니다.
- **`diamond.say()` 전면 교체:** 필요 여부를 별도로 검증할 기존 데이터 계약 작업입니다. 이번 공간형 선택 화면에 섞지 않습니다.
- **공유 파일 수정, 세이브 필드, 실제 브랜드, 새 의존성:** 모두 필요 없습니다.

**10. 밸런스 재측정 계획**

이번에는 계수 탐색보다 **변경 전후 동등성 확인**이 목적입니다.

비교 기준과 격자를 먼저 고정합니다.

- 기준: 동일 소스 버전의 변경 전과 변경 후.
- 능력치: 45·70·90·110·130·150.
- 컨디션: 20·50·80.
- 리그: 실제 리그 설정 전체, 상대 전력은 각 리그의 약·중·강 구간.
- 시즌 길이: 144·162경기.
- 조작: 무작위 선택, 단서가 있을 때 함정 회피, 한 구역 고정, 미선택, 실제 자동 경로.

검증 단계:

1. **판정 동등성:** 동일 난수·입력 재생에서는 판정 불일치 0건.
2. **단일 미니게임 측정:** 조건별 100만 회, 여러 시드에서 세 판정 비율 확인. 선택 난수와 게임 난수는 다른 시드 사용.
3. **시즌 측정:** 타율·안타·홈런·득점·도루·WAR 원값과 상한 도달률을 비교.
4. **후속 영향:** 타이틀·수상률, 연봉 분포, 사람과 라이벌 기록 비율, 가을야구 우승 곡선 비교.
5. **실제 사용성:** 구역 선택 시간·미선택률·단서 이해도를 확인. UI가 이해되면서 사람의 선택 전략이 달라질 가능성은 수학적 동등성과 별개로 측정.

같은 입력과 난수를 재생한 경우에는 평균 오차 허용폭이 아니라 **결과의 정확한 일치**를 요구합니다. 독립 몬테카를로 결과는 신뢰구간과 함께 보고합니다.

현재 실행한 것은 앞서 적은 기존 판정 모델의 100만 회 측정입니다. 새 구현·시즌 회귀·모바일 화면 검증은 아직 수행하지 않았습니다.
